## セキュリティ・法務/プライバシー観点（round 1）

### 前提の再確認（過大評価しないための線引き）

保持ゼロ化 Epic #162（`docs/design/stateless-architecture.md`・`docs/research/2026-07-28-data-retention-inventory.md`）により、
D1 時代の `2026-07-27-public-release-risk-cost.md` の R1〜R10 のうち **R3（消えない個人データの蓄積）・R4（ログアウトでトークン残置）・R9（D1 jurisdiction 未設定）はすでに解消済み**（D1 バインディング自体が撤去済み）。
これらを未解消として再度リスク計上しない。**現存するのは以下の 3 系統のみ** と整理する。

- サーバー中継リスク（トークンを一時的に平文で扱う立場そのもの）＝ 旧 R1/R2 相当（緩和されたが消えてはいない）
- GitHub App が単一の信頼点であることに由来するリスク＝旧 R5 相当
- workers.dev 運用に由来するエッジ防御欠如＝旧 R6（未解消。ドメイン方針そのもの）
- ポリシー文面と実装の整合＝旧 R7（大半解消・1 点残存を below で指摘）

---

### ① 現本番（workers.dev）をそのまま一般公開

**残存リスク（過大評価せず）**

1. **トークン中継者としての責任は「軽量化されたが消えていない」**（`data-retention-inventory.md` §2.2）。Worker は `/api/*` で毎リクエスト Cookie を復号し平文トークンをメモリ上で扱う。保持ゼロでも **処理中の露出面** は残る（漏洩の一撃性は下がったが、Worker 実行環境自体の侵害・依存パッケージの sc攻撃には無防御）。鍵ローテーション時に旧鍵の Cookie は復号不能→再ログインで済む設計（`worker/crypto.ts` の `sealVersioned`/`openVersioned`）は良い緩和だが、**鍵漏洩そのものを検知する手段（異常アクセス監視）は #172 待ち**（brief (c)）。
2. **GitHub App 単一障害点は解消されていない**（旧 R5）。`docs/requirements/00-requirements.md` PR-5（422 連発ユーザーの自動抑止）は SHOULD のまま未実装（brief (c) の #179 = 「サーバー側の起票ガード」が該当）。1 ユーザーのスパム起票で App が停止すれば **全利用者が同時に使えなくなる**（トークンを預からない設計でも、GitHub 側の信頼点は 1 つのまま）。GitHub 公式には「abuse detection で App/アカウントが自動制裁される」実例が多数あるが（[GitHub Community #191078](https://github.com/orgs/community/discussions/191078) 等）、「1 App = 全ユーザー停止」の公式ポリシー文書は見当たらず、**リスクの実在は合理的推定（レート制限 PR-4 は実装済みだが日次上限なし）** であり確度は「中」と評価する。
3. **workers.dev はゾーン機能（WAF・Rate Limiting Rules・Turnstile）を使えない** という前提（旧 R6）は Cloudflare 公式ドキュメントで明示的に「WAF 非対応」と書かれた一次情報は見つからなかった（[workers.dev routing docs](https://developers.cloudflare.com/workers/configuration/routing/workers-dev/) は「Free website として個人・趣味用途を想定」としか書いていない）。ただし Turnstile・WAF・Bot Management は Cloudflare の「ゾーン」単位機能であり、workers.dev はゾーンを持たない仕様上の帰結として使えないというのが実務上の共通認識（`2026-07-27-public-release-risk-cost.md` R6 の記述と整合）。**確度は「高いが一次情報での断定はできない」** としておく。実害は「未認証フラッドでもリクエスト数を消費する」点で、アプリ層レート制限（GitHub 認証必須・401 早期リターン）はあるが、無料枠の日次上限そのものには当たりうる。**#171（使用量アラート）が未実装のままだと「気づいたら止まっていた」が起きる**。
4. **法務面の残存 1 点（見落としやすい）**: `src/i18n/translations.ts` のプライバシーポリシー（7 節構成・P4 で更新済み）を確認したところ、**問い合わせ窓口（7 節）・保持期間（4 節）・基盤側記録（5 節）は明記済み** で `2026-07-27-public-release-risk-cost.md` R7 の当時の指摘は大半解消されている。しかし **Cloudflare が米国事業者であること・データが越境処理されることの明記が一切ない**（`米国`/`海外`/`アメリカ` で grep して 0 件）。個人情報保護委員会のガイドライン（[外国にある第三者への提供編](https://www.ppc.go.jp/personalinfo/legal/guidelines_offshore/)）では、外国にある事業者を「委託先」として使う場合（第三者提供ではなく委託）でも、**「外的環境の把握」として委託先が所在する外国の名称と当該国の個人情報保護制度の情報提供が求められる**（令和 4 年改正 Q&A）。本アプリは Cloudflare を委託先として使っている（トークンの独立利用はさせていない）ため 28 条の本人同意までは不要と整理できるが、**「外的環境の把握」の情報提供は別途必要**。ここは `docs/research/2026-07-27-public-release-risk-cost.md` §4 の「越境移転」論点がまだプライバシーポリシー本文に反映されていない、という **具体的な未了タスク** として指摘する（ファイル: `src/i18n/translations.ts` 2 節 or 新設 8 節に「Cloudflare（米国に本社を置く事業者）のインフラを利用しており、処理は日本国外でも行われうる」旨を追記）。

**評価**: 技術的な公開ブロッカーはない（brief (c) の通り GitHub App public 化・権限説明・PP/ToS 整備は完了済み）。残るのは **文書 1 点の追記** と **#171/#172/#179 の実装状況の確認**。「公開してよいか」は Yes、「無条件で今すぐ」は No（下記②の条件を満たしてから）。

### ② リポジトリのみ公開してセルフホスト方式

**セキュリティ・法務上の責任がどう動くか（本質的な比較軸）**

- **トークン中継者の責任が消える**: 各自が自分の GitHub App（またはOAuth App）を登録し、自分の Cloudflare アカウントにデプロイするため、**運営者（オーナー）は他人の GitHub トークンに一切触れない**。これは「持つことで発生する責任」（`2026-07-27-public-release-risk-cost.md` §2）を構造的にゼロにする、保持ゼロ化よりさらに一段強い解決。
- **法務責任も利用者ごとに分散する**: APPI・GDPR の「個人情報取扱事業者」はフォークして自分のインフラにデプロイした本人になる。オーナーは「コードの作者」であり「サービスの運営者」ではなくなるため、PR-1〜PR-3（利用規約・プライバシーポリシー・アカウント削除案内）はオーナー自身のサービスとしては不要になる（各自が必要なら自分で書く）。ただし **オープンソースの提供者としての一般的な免責（無保証条項・MIT 等ライセンスの Disclaimer）は引き続き必要**（`docs/requirements/00-requirements.md` PR-1 の思想を README/LICENSE に落とす形に付け替え）。
- **GitHub App 単一障害点も分散する**: 各自が自分の App を登録するため、1 人のスパムが全利用者に波及するリスクが消える（旧 R5 の根本解消）。
- **セルフホストの実務ハードルが新たなリスクに転化する**: `TOKEN_ENCRYPTION_KEY` の生成・Secrets 登録・OAuth App の Callback URL 設定など、セキュリティ設定を利用者自身が正しく行える保証がない。**誤設定（例: `TOKEN_ENCRYPTION_KEY` を弱い値にする、workers.dev の URL を推測されやすい命名にする）のリスクは利用者に転嫁されるだけで消えない**。README にセキュリティ設定のチェックリストを用意しないと「フォークしたら Client Secret が漏れた」を運営者が防げなくなる（ただし責任も転嫁されるので、オーナーにとってのリスクではなく利用者にとってのリスク）。
- ミッション KPI「初回セットアップ 5 分以内」（brief (f)）との衝突: GitHub App 登録・Secrets 設定・`wrangler deploy` を要求するセルフホストは、非エンジニアには 5 分で終わらない。**①（ホスト提供）はこの KPI を満たすが、③（セルフホストのみ）は満たさない**。ここは他レンズ（プロダクト側）と評価が割れる可能性がある。

### ③ 両方（ホスト版を運営しつつリポジトリも公開）

- セキュリティ・法務上は「①のリスクをそのまま抱えたまま、③の恩恵（分散オプションの提供）を追加するだけ」であり、**①のリスクを下げる効果はない**。ただし②のセルフホスト導線があることで、**トークンを他人に預けたくない・自分のインフラ内で完結させたい利用者に選択肢を提供できる** 点は良い緩和（プライバシー配慮を求める层への回避策）。README にセキュリティ設定チェックリストを用意する前提は②と同じ。

### ドメイン方針への意見

**workers.dev 継続を支持する（現時点ではカスタムドメイン取得は不要）**。根拠:

- OQ-7 は 2026-07-10 に決定済みで覆す新情報がない。`__Host-` Cookie 属性はホスト単位でありサブドメインでも安全性は変わらない（`docs/design/stateless-architecture.md` §4）。
- カスタムドメイン化の主目的は WAF/Turnstile 導入（旧 R6 の本格対応）だが、これは「無料枠のまま数千 DAU」の規模では過剰投資。保持ゼロ化でトークンを預かる期間がリクエスト処理中だけになった今、**エッジ防御の欠如は「なりすまし」ではなく「リソース消費・可用性」のリスクに性質が変わっている**（トークンは既に暗号化 Cookie 側にあり、WAF はそれを守るものではない）。であれば #171（使用量アラート）で十分にカバーできる。
- **カスタムドメイン化を「今回のトリガー」にすべき条件を明記**: TWA 化（M4）でアプリ的信頼性向上が必要になったとき、または実際に workers.dev の無料枠制限（Workers リクエスト 10 万/日）に到達が見えてきたとき。それまでは「ドメイン変更」という不可逆コスト（OAuth callback URL 変更・GitHub App 設定変更・利用者のブックマーク切れ）を払う理由がない。

### 他レンズが言いそうな楽観論への先制反論

- **「保持ゼロ化したのでリスクは実質ゼロ」への反論**: 保持ゼロは「盗まれたときの被害の永続性・鍵ローテーション不能」という **静的リスク** を消したのであって、**処理中の一時露出**（Worker 実行環境の侵害・依存パッケージの脆弱性）と **GitHub App 単一障害点** という **動的リスク** は別物で消えていない。R1/R2 は「軽量化」であって「解消」ではない（`data-retention-inventory.md` は D1 撤去の事実を述べているが、Worker が「復号→GitHub 呼び出し→破棄」する構造自体は残ると明記・§2.2）。
- **「GitHub App が public 設定・権限整備済みだからもう公開できる」への反論**: PR-6（App 設定）の完了は **入口の要件** であって、PR-5（スパム自動抑止）が SHOULD のまま未実装（#179）なのは **出口の要件** が空いたまま。1 ユーザーの悪用で App 全体が止まるシナリオは PR-4（レート制限）だけでは防げない（日次上限がないため「1 分 10 件を 24 時間回し続ける」= 14,400 件/日は技術的に可能）。
- **「個人開発・無償提供だから法務は最低限でよい」への反論**: 無償・個人開発であっても、EU 圏の利用者が使えば GDPR の管理者責任は発生し（brief に地域制限の言及なし＝グローバルに開放される前提）、APPI も事業規模を理由に適用除外にはならない（個人情報保護法に小規模事業者の適用除外規定はない。2015 年改正で撤廃済み）。「問い合わせ窓口すらない」状態は個人開発でも最低限の実務違反になりうる、という点は本アプリでは **P4 で既に手当て済み**（7 節）なので実害はないが、「無償だから何もしなくていい」という一般化には同意しない。
- **「workers.dev のままでも実害はない」への反論**: 現時点の DAU 規模では正しいが、brief (b) の「無料枠のまま数千 DAU」試算は **D1 時代の書き込みボトルネック前提** であり、D1 撤去後の実際のボトルネックは Workers リクエスト数（10 万/日）に一本化されている。ここへの到達可能性（未認証フラッド含む）を監視する #171 が未実装のまま「実害はない」と言い切るのは、**観測手段がないのに安全と主張している** 状態であり、公開前に埋めるべき条件からは外せない。
