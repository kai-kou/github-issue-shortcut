## product-adoption 主張（Round 1）

### ① 公開の目的は「未定義」ではなく、実は既に確定済み — ただし「配布」と「集客」は別レイヤー

「今回一般公開すべきか」という問いは新規判断ではない。要件定義 §1.3（`docs/requirements/00-requirements.md:30`）が「**最初から一般公開を前提とし、誰でも GitHub ログインで利用できる**」と明記し、これは 2026-07-10 の基盤決定であり M1〜M3（54+20+21 SP）はすでにこの前提でドッグフーディング済み（`docs/requirements/04-milestones.md:78-86` の M1 Done 判定で「新規ユーザーがログイン→App インストール→初起票を 5 分以内に完了できる」を実機確認済み・2026-07-25・#95）。GitHub App も既に public 設定・説明文・プライバシーポリシー整備が完了している（brief (c)・#173 クローズ済み）。

したがって①②の問いは「一般公開するか」ではなく実質「**今から積極的に集客・告知するか**」である。誰に届けたいかはリーンキャンバス（`docs/requirements/01-lean-canvas.md:11,32`）で既に定義済み: 第一号は開発者自身、次いで「GitHub Issues で個人タスク管理する Android 使いの開発者（Zenn/Qiita 読者層）」。チャネルも `01-lean-canvas.md:14,55-57` で「GitHub 公開リポジトリ + 日本語技術記事」と決まっている。**この前提を今崩す動機は brief に見当たらない**。もし security-legal / ops-cost が「まだ届けたい相手が曖昧」と主張するなら、それは公開可否の論点ではなく、未着手の運用ガード（#171/#172/#179）の話にすり替わっている可能性がある。

### ② 3 案が KPI（初回セットアップ 5 分以内）に与える影響 — 定量評価

**現行のホスト提供モデル（GitHub OAuth・PAT レス）**: リーンキャンバス `01-lean-canvas.md:87` の通り「セットアップ 0 分（OAuth のみ）」が謳い文句であり、M1 Done 判定で実機 5 分以内を確認済み（`04-milestones.md:85`）。これは **既に達成・検証済みの資産** である。

**リポジトリのみ公開・各自フォーク方式（案③）を採った場合の推定所要時間**（`docs/requirements/00-requirements.md` 6 章のアーキテクチャ + `04-milestones.md` M0 タスクから逆算。実測ではなく合理的推定であることを明記する）:

| ステップ | 推定所要時間 | 根拠 |
|---|---|---|
| リポジトリ fork + ローカル取得 | 2〜3 分 | 標準的な GitHub 操作 |
| 独自 GitHub App 新規作成（permissions・callback URL 設定） | 10〜15 分 | `00-requirements.md:145` の要求権限設定・callback URL は「デプロイ後の実 URL」が必要な鶏卵問題（`04-milestones.md:26` で本プロジェクト自身が「Setup URL は先に設定できない」と実測済み・#173）。フォーク者は同じ罠に毎回ハマる |
| Cloudflare アカウント作成（未保有の場合） | 5〜10 分 | メール確認等 |
| `wrangler.jsonc` の name/vars 書き換え（サブドメイン固有名が必要） | 3〜5 分 | `04-milestones.md:32-35` の M0 タスク（雛形構築だけで sp:5+sp:2+sp:2＝本チーム換算で数時間相当の作業） |
| `TOKEN_ENCRYPTION_KEY` 生成 + Workers Secrets 登録（CLI or ダッシュボード） | 5〜10 分 | `00-requirements.md:147` AES-256-GCM 鍵は非技術ユーザーには自明でない手順 |
| デプロイ → callback URL を実 URL に修正 → 再デプロイ | 5〜10 分 | 上記鶏卵問題の解消ループ |
| 初回エラー対応（依存バージョン相性・Secrets 未設定等） | 10〜30 分（変動大） | `04-milestones.md:50` に「Vitest 4 系必須などツールチェーン相性」がリスクとして明記されており、フォーク者にも同じ相性問題が起きうる |

**楽観合計（経験者・エラーなし）で約 30〜45 分、非技術者や初回 Cloudflare/GitHub App 利用者では 1〜2 時間超、離脱の可能性が高い。** これは KPI 目標（5 分以内）の **6〜24 倍以上** であり、目標の桁が違う。しかも「セットアップ」の定義（`project-mission.md:18` 初回セットアップ完了率＝ログイン→初起票 5 分以内）は「ログイン後」のみを指すが、フォーク方式ではその手前に「GitHub App 作成 + デプロイ」という **要件定義に存在しない新規工程** が挟まる。KPI の測定対象自体が変質してしまう。

**結論**: 案③（リポジトリのみ公開・セルフホスト必須）を「一般公開の唯一の手段」にすることは、ミッション KPI を事実上放棄する選択であり、リーンキャンバスの差別化要因そのもの（`01-lean-canvas.md:87`「セットアップ 0 分」）を自ら破壊する。案①（現行ホスト継続）が KPI 適合の唯一の現実解。

### ③ ドメインが体験・信頼に与える影響

OQ-7 は既に「workers.dev 継続・カスタムドメインは取得しない」と決定済み（`00-requirements.md:330`）。product-adoption の観点から再検討の必要性を検証したが、**覆す積極的理由はない**。

- PWA インストール後の体験（ホーム画面アイコン・スタンドアロン起動）では URL は表示されない。アプリ名は `vite.config.ts:66` で `"GitHub Issue Shortcut"` / short_name `"Issue Shortcut"` と設定済みで、これが利用者の目に触れる主要な識別子になる。URL の見た目が効くのは「初回ログイン前にアドレスバーを見る瞬間」と「GitHub 認可画面（GitHub 自身のドメインなので影響を受けない）」に限られる
- ターゲット層（`01-lean-canvas.md:32` Zenn/Qiita 読者層の開発者）は `*.workers.dev` を「個人開発 Cloudflare Workers アプリ」の記号として認識できる技術者であり、一般消費者向けサービスほど workers.dev サブドメインを不審に思わない。市場リサーチ（`docs/research/2026-07-10-market-competitors.md`）が示す通り、この製品はそもそも「実用ツール / OSS」（`01-lean-canvas.md:61`）であり信頼度が問われるのは「コードを検証できるか」（OSS 公開性）の方であって、ドメインの見た目ではない
- 唯一ドメインが効くのは M4（TWA / Play 配布）局面（Digital Asset Links の都合）だが、M4 は「実施判断保留」と既に決定済み（`04-milestones.md:15,168`）。今カスタムドメインを取得するのは、使うかどうか未定の将来オプションのために先出しコストを払うことになり、ミッションの YAGNI 判断基準（`project-mission.md:27`「まず自分が毎日使える最小構成。汎用化は後」）に反する

**結論**: ドメインは workers.dev 継続が妥当。再検討はカスタムドメインが必要になる具体的事象（TWA 着手判断）が発生してから。

### ④「今は公開しない/限定公開」という選択肢の評価

この選択肢には 2 つの読み方があり、混同を避ける必要がある。

- **読み方 A「一般公開の前提そのものを撤回し非公開に戻す」**: 支持しない。要件定義の基盤決定（§1.3）を覆し、M1〜M3 で実機検証済みの成果（54+20+21 SP）を無効化する重い decision であり、brief に新規のトリガー（重大インシデント等）は存在しない。ミッションの「まず自分が毎日使える」（`project-mission.md:27`）は既に満たされている（オーナー自身がドッグフーディング中）が、これは「非公開に戻す理由」ではなく「一般公開は既に前提として組み込まれている」ことの追認材料である
- **読み方 B「技術的には公開状態のまま、能動的な告知・集客だけ保留する」**: 支持する。現状は GitHub App が public 設定でも、Zenn/Qiita 記事等の能動的チャネル（`01-lean-canvas.md:14`）はまだ実行されていない。brief (c) に残る 3 件の未実装ガード（使用量アラート #171・アカウント保護手順 #172・サーバー側起票ガード #179）は、**運用が個人 1 人（brief (g)・オンコールなし）である以上、能動的な集客で流入が増える前に閉じておくべき前提条件** であり、product-adoption の視点からもこれに同意する。KPI 未達のまま人を呼び込むと「初見ユーザーが詰まって離脱する」体験の方がブランド毀損として重い（市場リサーチ `market-competitors.md:12` の Anywhere Issue「連携後リポジトリが出ない」致命的レビュー事例が反面教師）

**推奨**: 「公開するかどうか」の二択ではなく、「技術的公開（既に完了）」と「能動的告知（#171/#172/#179 クローズが前提条件）」を分離した段階公開が KPI・持続運用の両面で最も合理的。

### ⑤ 他レンズ（セキュリティ・コスト）の慎重論への反論

security-legal / ops-cost が「リスク・コスト面から公開を遅らせる、またはセルフホスト方式に倒すべき」と主張してきた場合を想定した反論:

- **「セルフホストにすればリスク・運用負荷が減る」への反論**: 案③はオーナーの運用責任を軽減しない。各フォーカーが自分の GitHub App・Cloudflare アカウントを作る以上、悪用対策（PR-4/PR-5）・鍵管理・監視は各自が個別に（多くの場合本家より低い品質で）再実装することになり、**製品としての事故は減らず、むしろ「本家より緩い設定の乱立」という新しい低品質サーフェスを生む**。セキュリティ上の余caution は「案③への逃避」ではなく「案①のまま #171/#172/#179 を閉じる」ことで対応すべきで、これは KPI を犠牲にしない解
- **「コストが心配なら公開を遅らせるべき」への反論**: brief (b) の通り無料枠のまま数千 DAU まで耐える試算があり、かつ D1 撤去後はさらに余裕がある。市場リサーチ（`market-competitors.md:44-47`）は市場規模自体が小さいこと（競合 3 アプリの評価件数が各 3 件程度）を示しており、急激なコスト超過シナリオの蓋然性は低い。コスト慎重論は「使用量アラート（#171）を先に付ける」で十分吸収でき、公開可否や配布方式の変更を要する規模の懸念ではない
- 総括: セキュリティ・コストどちらの慎重論も「案③への転換」や「一般公開の撤回」を正当化する強さはなく、せいぜい「#171/#172/#179 を能動集客の前提条件にする」（④の推奨と一致）レベルの手当てで足りる
