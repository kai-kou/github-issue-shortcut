## oss-selfhost Round 2（rebuttal / concession）

### 1. product-adoption「セルフホストは初回セットアップ KPI を破壊するので非推奨」への応答 — **概ね concession、ただし枠組みを訂正**

product-adoption の見積もり（fork+取得 2〜3分／GitHub App 作成 10〜15分／Cloudflare アカウント 5〜10分／`wrangler.jsonc` 書き換え 3〜5分／鍵生成+Secrets 5〜10分／callback URL 修正ループ 5〜10分／初回エラー対応 10〜30分＝楽観合計30〜45分）と、私が round 1 で実装ファイルから直接洗い出した見積もり（25〜40分・鶏卵問題でつまずくと+15〜30分）は、**別のアプローチ（要件文書からの逆算 vs 実装コードの直読）で独立に出したにもかかわらずほぼ一致する**。特に「callback URL の鶏卵問題」を両者が独立に最大の詰まりどころと特定した点は、この障壁が推測ではなく構造的事実であることの裏付けになる。

→ **KPI 未達という結論そのものには同意する（concession）**。「案③（フォーク方式）を一般公開の唯一の手段にする」ことがミッション KPI を破壊するという主張に反論の余地はない。

ただし 1 点、枠組みを訂正したい: product-adoption の主張は暗黙に「KPI＝全公開手段が満たすべき単一の物差し」という前提に立っているが、round 1 で述べた通り **フォーク方式は「ログイン→初起票 5 分」という KPI が測定対象にしている体験（`project-mission.md:18` の定義はログイン後を指す）の外側にいる別ペルソナ向けの配布経路** である。product-adoption 自身も④で「技術的公開（既に完了）」と「能動的告知」を分離しているのと同じ構造で、私は「ホスト提供（KPI 対象）」と「セルフホスト手順の存在（KPI 対象外・信頼材料としての情報提供）」を分離すべきだと考える。これは反論ではなく、**同じ結論（案①を主軸にする）に至る理由付けの補強** として読んでほしい。両者の分析を合わせると「案③単体は不可・案①が主軸・セルフホスト手順は案①に対する補助的な信頼訴求として小さく用意する」という一致点がより強固になる。

### 2. security-legal「セルフホストで責任が分散する」への反論 — **法的責任は分散するが、実務上の負荷は本家に返ってくる**

security-legal は②で「GitHub App 単一障害点も分散する」「オーナーは他人の GitHub トークンに一切触れない」「法務責任も利用者ごとに分散する」と評価しつつ、末尾で「セルフホストの実務ハードルが新たなリスクに転化する…誤設定のリスクは利用者に転嫁されるだけで消えない（ただし責任も転嫁されるので、オーナーにとってのリスクではなく利用者にとってのリスク）」と結論している。

**この最後の一文（「オーナーにとってのリスクではない」）に反論する。** round 1 の③（フォーク方式の隠れコスト）で具体化した通り、責任の法的所在が移っても、実務上は以下の 2 経路で本家に押し戻ってくる:

- **サポート issue の流入**: フォーク先の Callback URL 不一致・Permissions 設定ミスは、issue 起票者からは「GitHub Issue Shortcut というアプリの不具合」にしか見えない。法的責任は利用者本人にあっても、**本家のオーナーが issue トリアージ・返信という実作業コストを払う** 構造は変わらない。これは security-legal の評価軸（法的責任の所在）には現れないが、`session-sprint-rules.md` が前提にする「運用は個人 1 人」（brief (g)）という制約下では実質的なコストである
- **複製 App による評判の混乱**: round 1 で指摘した通り、フォーク先が GitHub App 名を "GitHub Issue Shortcut" のまま流用すると、脆弱な設定による事故が「本家の製品名」で言及されるリスクがある。security-legal の法務評価（APPI/GDPR の管理者責任）は正しく「利用者本人が個人情報取扱事業者になる」と結論しているが、**レピュテーションリスクは法的責任とは別軸で本家に残る**。この軸は security-legal の②に欠落している

つまり「責任が分散する」は法務・データ保護の観点では正しいが、**「オーナーのリスクがゼロになる」は言い過ぎ** であり、セルフホスト経路を案として採用するなら、README に「GitHub App 名はフォーク時に変更すること」という運用ガイドを添えることが、security-legal の言う責任分散を実際に機能させるための **前提条件** になる（現状はガイドが無いため、責任分散は理論上のみで実務上は不完全）。

### 3. 「リポジトリ公開」と「セルフホスト推奨」の分離 — 露出物（ハーネス・議論記録・`content/`）への対処は現実的か

round 1 の④で「コードそのものの公開に構造的な機密漏洩は見当たらない」と結論したが、この Round 2 で一点補足する。**対処の現実性は「今」と「フォークが実在した後」で非対称である**。

- `content/pipeline-state/cost_log.jsonl` 等の実額コストデータは、**今後の追記を止める（`.gitignore` 化）ことは容易** だが、**過去分を消すには git 履歴の書き換え（force-push・history rewrite）が要る**。現在は `forks_count:0` （round 1 で実測済み）なので history rewrite の副作用（fork 側の履歴分岐・commit SHA 変化）はまだ発生しない。**この「安く直せる窓」は他者が実際にフォークした瞬間に閉じる**。したがって「セルフホストを推奨し始める前」に済ませておくべき順序依存のタスクであり、⑤の推奨に「history rewrite は fork が実在する前に」という時限条件を追加したい
- `content/discussions/*`（本議論を含む過去の議論型レビュー全文）は事情が異なる。ここには security-legal が round 1 で挙げた「GitHub App 単一障害点」「workers.dev のエッジ防御欠如」等の **弱点分析そのもの** が第三者に読める形で残る。これは削除・非公開化が現実的ではない: (a) 本リポジトリの運用スタイル自体が「議論記録を Issue/PR コメントに残す」ことを前提にしており（`session-compression-rules.md`）、選択的に隠すと自己矛盾を起こす、(b) 弱点の記述を消しても実際の脆弱性（例: PR-5 未実装）はコードを読めば同じ第三者が気づける。**「議論記録に書いてあるから危険」ではなく「弱点そのものが未対策だから危険」であり、対処すべきは記録の隠蔽ではなく security-legal が挙げた #171/#172/#179 の実装そのもの** という結論になる

→ 結論: `content/` 配下の露出対応は「コストログ（今すぐ・fork前が締切）」と「議論記録（対応不要・実体の脆弱性解消で代替）」に分けて扱うのが現実的。ひとくくりに「公開前にクリーンアップが必要」と扱うと、後者を理由に公開判断そのものを不必要に遅らせてしまう。
