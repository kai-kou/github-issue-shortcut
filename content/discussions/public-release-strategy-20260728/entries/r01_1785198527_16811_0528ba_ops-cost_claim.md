# ops-cost（運用コスト・可用性）Round 1

## 0. 結論先出し

D1 撤去後、**コスト構造は「D1 書き込み支配」から「Workers Requests 支配」に完全に入れ替わった**。天井（無料枠が尽きる DAU）は上がり（約 2,400 → 約 6,600 DAU）、スケール時の実額コストは旧試算の 1/7〜1/11 に下がる。つまり **コストはこれまで以上に心配材料ではない**。一方で天井に当たったときの挙動は「静かな全停止（Error 1027・最大 24h）」であり、監視ゼロ（#171）はコストの話ではなく **可用性の話として重大**。ドメイン取得は Cloudflare の課金プランとは無関係に約 1,500〜1,600 円/年で完結し、ゾーン化で得られる防御（WAF 基本ルール・Rate Limiting 1 本・Turnstile）は無料ゾーンプランの範囲で足りる可能性が高い。

## ③ ドメインの費用対効果

| 項目 | workers.dev 継続 | カスタムドメイン取得 |
|---|---|---|
| 年額（ドメイン登録） | $0 | **.com 実測 $10.44/年**（Cloudflare Registrar at-cost・ICANN 手数料 $0.18 込み。2026-07-28 WebSearch 確認）。**.dev の実額は本セッションで一次情報を取得できず「根拠不明」** |
| ゾーン利用料 | 不要（ゾーン化しない） | **$0（Free ゾーンプランのまま可）**。Cloudflare の Free/Pro/Business は「ゾーン（サイト）プラン」であり Workers Paid（$5/月）とは別課金軸。ドメインを Cloudflare にゾーン追加するだけなら追加の月額は発生しない（2026-07-28 WebSearch 確認） |
| WAF | 使えない | **Free ゾーンプランでも「Cloudflare Free Managed Ruleset」（高インパクトな脆弱性のみ対象の basic サブセット）が既定で有効**。OWASP Core Ruleset・ルールのカスタマイズは Pro（$20〜25/月）以上が必要（2026-07-28 WebSearch 確認） |
| Rate Limiting Rules（エッジ） | 使えない | **Free ゾーンプランで 1 ルールのみ**（Pro は 2 ルール、Business は 5 ルール・10 分ウィンドウ）。本アプリが守りたいエンドポイントは実質 `/auth/login` と `/api/issues` の 2 系統（`worker/index.ts` 185・373 行目）なので、Free の 1 ルールでは **両方は同時にカバーしきれない**可能性がある（2026-07-28 WebSearch 確認・ただし本アプリ既存のアプリ層レート制限＝Workers Rate Limiting binding は残るため二重防御の「上乗せ」ではある） |
| Bot 管理 | 使えない | Free ゾーンプランは「Bot Fight Mode」（基本的な自動化検知・チャレンジ）のみ無料。「Super Bot Fight Mode」（きめ細かい制御）は Pro 以上。**Enterprise 級の Bot Management は本アプリの規模では過剰** |
| Turnstile | 使えない（カスタムドメイン不要でも技術的には設置可能だが、workers.dev では widget 設置の実務的な意味が薄い） | **無料枠が広い（月間 100 万 solve まで無料・サイトキー数無制限）**。ゾーン化そのものは前提条件ではない（2026-07-28 WebSearch 確認） |
| 合計・実質追加コスト | **$0** | **ドメイン代のみ（.com 換算で約 1,600 円/年 ≒ 133 円/月）。Free ゾーンプランに留まる限り Cloudflare 側の追加課金は発生しない** |

**結論**: 「カスタムドメイン化 = Pro プラン以上が要る」という思い込みは誤り。**WAF 基本ルール・Rate Limiting 1 本・Turnstile・Bot Fight Mode はいずれも無料ゾーンプランの範囲**で使える。実コストはドメイン登録料（年 1,500〜1,600 円程度、TLD 次第）だけであり、要件 OQ-7（`docs/requirements/00-requirements.md` 330 行目・「カスタムドメインは取得しない」2026-07-10 決定）の再検討条件だった「TWA 検討時」を待たずとも、**費用面のハードルは実質存在しない**。ただし Free の Rate Limiting 1 ルールでは 2 エンドポイントを両方エッジ側で守り切れない可能性があり、これは費用ではなく **機能制約**として残る。

## ④ 監視未設定（#171）で起きる失敗シナリオ（数値付き）

1. **無料枠の Requests 上限到達で「静かな全停止」**: Workers Free プランは 100,000 requests/日を超えると **Error 1027** を返し、**00:00 UTC（09:00 JST）のリセットまで完全復旧しない**（2026-07-28 WebSearch 確認）。現在の DAU 換算天井は約 6,600（§②）。使用量アラート・予算ガード未実装（`docs/requirements/00-requirements.md` 191 行目 NFR-14 の「枠超過が近づいたら検知できること」が未達）のため、**運営者はアプリが落ちていることに利用者からの申告以外で気づく手段がない**。一人運用（brief (g)）のため、気づくのが翌朝以降になる想定は十分あり得る。
2. **想定される到達経路は「成功」と「攻撃」の両方**: 6,600 DAU は決して極端な数字ではない（Twitter/X 等での紹介 1 回でも短時間の急増はあり得る）。逆に、workers.dev には WAF が無いため（§③）、**未認証フラッドが Requests 枠だけを消費して同じ Error 1027 を引き起こせる**（`docs/research/2026-07-27-public-release-risk-cost.md` R6 行・93 行目「未認証フラッドでも **リクエスト数は消費する**」と整合）。つまり悪意の有無に関わらず同じ壊れ方をする。
3. **復旧確認の手段もない**: Analytics Engine 等の計測バインディングは未導入（`docs/research/2026-07-27-public-release-risk-cost.md` 21 行目）。ダッシュボードを能動的に見に行かない限り、リセット後に正常化したかどうかも分からない。
4. **数値的インパクト**: 全停止時間の期待値は「検知手段ゼロ」を仮定すると 0〜24 時間（発生タイミングと運営者の生活サイクル依存）。ミッション KPI（初回セットアップ 5 分・起票 10 秒）の観点では、**新規ユーザーの初回体験がまさにこの停止時間帯に当たった場合、離脱コストが最大化する**（初見で使えないアプリは再訪されない）。

**対策コストは実質ゼロ**: Cloudflare の使用量アラート（Notifications）自体は無料枠でも設定可能で、実装コストは低い（#171 が既に Issue化 済み）。ここは「コストが天井」ではなく「未実装であること」が問題であり、公開前提条件として費用対効果が最も高い項目。

## ⑤ 3 案の運用負荷比較

| 観点 | ①現行そのまま公開（host-only） | ②リポジトリのみ公開（repo-only・セルフホスト） | ③両方（host + repo 公開） |
|---|---|---|---|
| Cloudflare 側の運用対象 | **1 アカウント**（自分のみ）。§①②の数値がそのまま適用される | 各利用者が各自の Cloudflare アカウントで運用 → **運営者の運用負荷は増えない**（Issue Shortcut 側は関与しない） | 自分のホスト分は①と同じ負荷。加えてフォーク先の質問・環境差分デバッグの問い合わせ流入リスク（数値化不能・**根拠不明**、実績なし） |
| コストの帰属 | 運営者 1 人に集中（ただし §①②の通り極小: 無料〜$5/月で数万 DAU まで対応） | **利用者ごとに分散**（1 人あたり自分の無料枠内で収まる規模が確実なので、事実上ほぼ全員 $0） | 集中と分散が並存。ホスト版の運用負荷は減らない |
| 監視・可用性責任 | 運営者 1 人が全利用者分の可用性に責任（§④のリスクが全利用者に波及） | 各利用者が自分の分だけに責任（障害の影響範囲が利用者 1 人に限定される・**責任分散という設計上の利点**） | ホスト版利用者は①と同じ集中リスクを負う |
| 追加で必要な運用作業 | 使用量アラート設定・アカウント保護（#172）・起票ガード（#179） の 3 件（費用ほぼゼロ・工数小、§④） | 運営者側の追加運用作業は **ほぼゼロ**（GitHub App 新規作成・Secrets 設定などはすべて利用者側作業。ただしこれはコストではなく普及面の負荷なので oss-selfhost/product-adoption の担当領域） | ①の作業に加えて何もしなくてよい（②相当の分は利用者に転嫁されるため運営者コスト増にはならない） |
| コスト構造上の懸念点 | **無い**（§①②の通り、数千〜数万 DAU まで実額コストは軽微） | 運営者コストの懸念は無い（そもそも運営者のインフラを使わない） | 運営者コストの懸念は①と同じで無い |

**ops-cost レンズからの一言**: 3 案のどれを選んでも、**Cloudflare の実額コストが意思決定のボトルネックになることは無い**（D1 撤去後は特に）。差がつくのは「可用性の責任がどこに集中するか」であり、これは費用の問題ではなく §④ の監視体制の問題に帰着する。したがって ops-cost の立場からは、**host-only の実行可否はコストではなく #171（使用量アラート）の実装有無で判断すべき**、という点を強調したい。
