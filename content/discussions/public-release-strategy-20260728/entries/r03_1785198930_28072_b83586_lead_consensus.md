## 合意（lead 整理・2026-07-28 JST）

### 0. 議題の前提が 1 つ覆った（全員の議論の土台）

`oss-selfhost` が GitHub API で実測（`repo:kai-kou/github-issue-shortcut` → `"private": false, "visibility": "public", "forks_count": 0, "license": mit`）。
**リポジトリは既に public** であり、オーナーの問い③「リポジトリのみ公開して各自フォーク方式にするか」は
**未実行の選択肢ではなく、片側（公開）が既に実行済みの事実**。したがって残る決定は次の 2 つに絞られる。

- (A) 現本番（`https://github-issue-shortcut.kinamocchi-tech.workers.dev`）を **自分以外の利用にも供し続けるか**
- (B) セルフホストを **どこまで能動的に推奨・支援するか**（README 手順・Deploy ボタン・テンプレート化）

### 1. 合意した点（4 レンズが収束）

| # | 合意事項 | 収束の経緯 |
|---|---------|-----------|
| C-1 | **セルフホストを「唯一の提供手段」にするのは不可** | `oss-selfhost` が実装から洗い出した所要 25〜40 分（鶏卵問題でつまずくと +15〜30 分）と、`product-adoption` が要件文書から逆算した 30〜45 分（非技術者は 1〜2 時間超）が **独立に一致**。両者とも「GitHub App の Callback URL 鶏卵問題」を最大の詰まりどころと特定した |
| C-2 | **GitHub App の作成は自動化できない** | Deploy to Cloudflare ボタンで Cloudflare 側（fork・CI 配線・vars）はほぼ自動化できるが、GitHub App の作成は Cloudflare の管轄外。Manifest flow でも「Create GitHub App」の最終クリックは GitHub の意図的な設計で省略不可、かつ受け皿サーバーの新規実装・保守が要る |
| C-3 | **推奨は「両方」**（ホスト提供を主軸 + セルフホスト手順を補助として整備） | `oss-selfhost` ⑤ と `product-adoption` ②⑤ が別ルートで同一結論。ホスト提供は KPI 適合の唯一の現実解、セルフホストは別ペルソナ（開発者）向けの信頼材料 |
| C-4 | **技術的な公開ブロッカーは存在しない** | GitHub App は public 設定・権限理由・PP/ToS URL 整備済み（#173 クローズ済み）。保持ゼロ化（Epic #162）で旧 R3 / R4 / R9 は構造的に消滅 |
| C-5 | **#171（使用量アラート）が最優先の前提条件** | 3 レンズが独立に同じ Issue を境界条件として名指し。NFR-14 は MUST 要件で、未達のまま「安全」と言うのは **観測手段がないのに安全と主張している** 状態 |
| C-6 | **ドメインは workers.dev 継続。ただし理由は「コストが高いから」ではない** | `ops-cost` の実測でカスタムドメインの実費はドメイン登録料のみ（.com で年 $10.44 ≒ 約 1,600 円）、WAF Free Managed Ruleset・Rate Limiting 1 ルール・Turnstile は **Free ゾーンプランの範囲で使える** と判明。`security-legal` は round 1 の「過剰投資」という理由付けを撤回し、根拠を差し替えた |
| C-7 | **workers.dev リスクの実体は「攻撃されやすさ」ではなく「可用性の検知不能性」** | 保持ゼロ化でトークンは暗号化 Cookie 側にあり WAF が守る対象ではない。実害は Requests 上限到達時の Error 1027（00:00 UTC まで最大 24 時間の全停止）で、これは WAF の有無ではなく **監視の有無** で決まる |

### 2. 議論を経て修正・撤回された主張（相互検証の成果）

- `ops-cost`: D1 撤去でコスト構造が **「D1 書き込み支配」から「Workers Requests 支配」に入れ替わった** ことを再計算し、無料枠の天井が **約 2,400 DAU → 約 6,600 DAU** に上がったと訂正（1 ユーザーあたり限界コストは約 1/11 に低下）。brief (b) が引いていた旧試算は D1 前提のため更新が必要。
- `security-legal`: ドメイン方針の理由付けを「コストが高い」から **「切替の不可逆コスト（OAuth callback URL 変更・GitHub App 設定変更・利用者のブックマーク切れ）」＋「Free tier の Rate Limiting は 1 ルールのみで `/auth/login` と `/api/issues` の両方を守り切れない（防御が部分的）」** に差し替え。
- `product-adoption`: ① セルフホストを「KPI 違反」と断罪した図式を修正し、**KPI（初回セットアップ 5 分）は persona B 向けの指標でフォーク方式は測定対象外** と譲歩。② カスタムドメインを「TWA 判断待ちに固定」した結論を撤回し、**#171 実装後に再評価する第二の安全網** へ格上げ。③ #179（PR-5 スパム自動抑止）を「PR-4 があるから十分」と楽観視していた点を撤回。
- `oss-selfhost`: `security-legal` の「セルフホストで責任が分散する」に条件を追加。**法的責任は移っても、サポート issue の流入と GitHub App 名称衝突によるレピュテーションリスクは本家に返る**。
- `security-legal`: 上記を受け、責任分散を **2 軸に分離** して整理し直した（「オーナーの法的・トークン中継責任は分散する」／「エコシステム全体の脆弱性表面はむしろ増えうる」は両立する）。

### 3. 残った対立点（解消しなかった差分）

| 論点 | 対立の中身 | lead の裁定 |
|------|-----------|-----------|
| #171 は「公開可否の条件」か「集客の条件」か | `security-legal` は NFR-14（MUST）未達＝要件を満たした公開ではないと主張。`product-adoption` は技術的公開は既に完了しており能動告知の条件だと主張 | **実務上は同じ**（能動告知をしない現状は事実上ゼロ流入）。ただし「MUST 未達の状態を放置している」という `security-legal` の指摘は正しく、#171 は最優先で閉じる。呼び方の差は結論を変えない |
| ドメイン再検討のトリガーの強さ | `security-legal` は workers.dev 継続を維持（Free tier でも防御は部分的）。`product-adoption` は #171 後に費用対効果を再評価する対象へ格上げ | **今は取得しない** で一致しているため、再検討条件を「#171 実装後、または TWA 着手判断時」と明記して両論を吸収する |

### 4. 確度の弱点として残すもの（誠実に記録する）

- 「workers.dev ではゾーン機能（WAF・Rate Limiting Rules・Turnstile のエッジ適用）が使えない」を **名指しで断定した Cloudflare の一次情報は、`security-legal` / `ops-cost` の双方とも発見できなかった**。ゾーン単位機能であることからの実務上の共通認識どまりで、確度は「高いが断定不可」。
- Deploy to Cloudflare ボタンで **Workers Secrets の入力プロンプトが実際に出るか** は未検証。`.dev.vars.example` を既に持つため実装コストは小さい可能性が高いが、検証前に「自動化済み」と謳わない。
- 1 リクエストあたりの実 CPU 時間はリポジトリに実測記録がない（`ops-cost` が「根拠不明」と明記）。

### 5. 議論中に見つかったスコープ外の課題（別 Issue 化を推奨）
