## ② 自動化できる範囲 / できない範囲

一次情報: [Deploy to Cloudflare buttons](https://developers.cloudflare.com/workers/platform/deploy-buttons/)、[2025-04-08 changelog](https://developers.cloudflare.com/changelog/post/2025-04-08-deploy-to-cloudflare-button/)、[GitHub App manifest flow](https://docs.github.com/en/apps/sharing-github-apps/registering-a-github-app-from-a-manifest)（WebSearch/WebFetch で確認済み・2026-07-28 時点）。

| 領域 | 自動化可否 | 詳細 |
|------|----------|------|
| リポジトリの Fork/複製 | ✅ 自動 | Deploy to Cloudflare ボタンが「利用者の GitHub/GitLab アカウントへ複製」を実行 |
| Cloudflare リソースのプロビジョニング（KV/D1/R2/DO） | ✅ 自動（ただし**本アプリは対象外**） | `stateless-architecture.md`（P4・#166）で D1 を含む永続層を全廃済みのため、そもそもプロビジョニング対象が無い。これは**フォーク障壁を実質下げている**ポジティブな事実（以前の D1 時代なら DB マイグレーション適用が追加の手作業だった） |
| Workers Builds の Git 連携（CI/CD 配線） | ✅ 自動 | ボタン経由なら配線込みでデプロイまで完了 |
| `vars`（`GITHUB_CLIENT_ID` 等の非秘匿値） | ✅ 自動（プロンプト入力） | Cloudflare 側ドキュメントは `wrangler.jsonc` の `vars` をデプロイ時に自動処理すると説明 |
| Workers Secrets（`GITHUB_CLIENT_SECRET` / `TOKEN_ENCRYPTION_KEY`） | 🟡 **部分自動（要検証）** | ドキュメントは「`.dev.vars.example` / `.env.example` の dotenv 形式で secrets を定義でき、デプロイ時に値入力を促せる」と説明するが、プロンプト UI が確実に出るかは一次情報だけでは断定できない（要実機確認）。本リポジトリは `REPO/.dev.vars.example` を既にその形式で持っているため、**ボタンを追加する実装コストは小さい可能性が高い**が、動作検証なしに「自動化済み」と謳うのは時期尚早 |
| **GitHub App の新規作成そのもの** | ❌ 自動化不可（Cloudflare の管轄外） | Cloudflare は GitHub Apps/OAuth Apps の作成に一切関与しない。GitHub 側の Manifest flow（利用者を `github.com/settings/apps/new` へ POST 遷移させ、事前入力済みの App 作成画面を出す）は**入力の事前充填**はできるが、**「Create GitHub App」ボタンをユーザー本人が手でクリックする最終確認は省略できない**（GitHub 側の意図的なセキュリティ設計）。さらに Manifest flow を使うには、コールバックで返る一時 `code` を `POST /app-manifests/{code}/conversions` に交換する**受け皿サーバーを自分で用意して運用する必要がある**（本プロジェクトが新たに実装・保守すべき追加コンポーネント） |
| **Callback URL の鶏卵問題（①手順 3/9）** | ❌ 自動化不可 | Worker の実 URL が確定する前に GitHub App を完成させられないという順序制約は、ボタン化しても消えない構造的な問題 |

**結論**: 「ワンクリックで完全セルフホスト」は実現できない。Cloudflare 側（ホスティング）は Deploy ボタンでほぼ自動化できるが、**GitHub App 作成という GitHub 側の手作業が必ず残る**。これは実装で埋められない領域であり、README に「① ボタンを押す ② GitHub App を作る（手順書リンク）③ URL 発行後に Callback URL を直す」という **2 段階ガイド**として明示するのが現実的な最善。

## ③ フォーク方式の隠れコスト

- **サポート issue の流入**: 「ログインできない」「起票が失敗する」系の issue は、実際には利用者自身の GitHub App 設定ミス（Callback URL 不一致・Permissions 不足）であることが大半になる想定だが、issue 起票者にはオーナー本体の不具合と見分けがつかない。オーナーは他人の Cloudflare/GitHub App 設定を覗けないため**再現も遠隔デバッグもできず**、`/health` 的な自己診断（①手順 10）を案内する以上のことがしづらい
- **環境差分のデバッグ**: `wrangler.jsonc` の `ratelimits`（`REPO/wrangler.jsonc:28-45`）・`observability`（同 46-58）はフォーク先でも同じ値が引き継がれるが、フォーク先のトラフィック傾向次第では意味を持たない設定になりうる（例: 無料プランの Rate Limiting binding 上限、Workers Paid 未契約なら observability retention が 3 日固定 — `stateless-architecture.md:151`）。「なぜ自分の環境では挙動が違うのか」の切り分けコストは fork 側・本家側の双方に発生する
- **アップストリーム追随**: フォークは `git fetch upstream` を能動的に回さない限り更新が来ない。特にセキュリティ修正（例: 将来 `TOKEN_ENCRYPTION_KEY` の取り扱いに脆弱性が見つかった場合）が**フォーク先には自動で届かない**。Dependabot（`REPO/.github/dependabot.yml` 確認済み）は依存パッケージの更新は検知するが、本体コードの修正までは検知しない
- **複製 App による GitHub 側の混乱**: 各フォーカーが独自の GitHub App を作る設計自体は問題ないが、命名を "GitHub Issue Shortcut" のまま複数人が使うと、GitHub の認可画面（"〇〇 by 開発者名 wants to access your account"）でユーザーが本家と別物であることに気づきにくい。名称ガイドラインで「フォーク時は別名にする」を明示しないと、本家の評判に対する取り違えリスクがある
- **脆弱な設定が本家の評判に返る**: フォーク先が `TOKEN_ENCRYPTION_KEY` を弱い値のまま使う・Permissions を過剰に広げる等をした場合の実害は当人限定だが、「GitHub Issue Shortcut で被害が出た」という形で言及されるリスクはゼロではない（README 免責文言・SECURITY.md の対象外明記で軽減可能。`REPO/SECURITY.md:16-19` は既に依存脆弱性を対象外にしているが、フォーク先の設定不備は明記されていない）

## ④ リポジトリ公開単体の価値／公開時に露出するものの棚卸し

### 価値
- **コード監査可能性**: 本アプリはユーザーの GitHub トークンを Worker が一時的に復号して中継する構造（`stateless-architecture.md` §4-5）。ソースが公開されていること自体が「サーバーにトークンを保存していない」という主張の**検証可能性**を利用者に与える。これは security-legal レンズの「信頼できるという主張」を補強する材料であり、非公開のままでは「口頭の主張」に留まる
- **MIT ライセンス**（`REPO/LICENSE`）は改変・再配布・商用利用を制限しない。既に public 化・MIT 化されているため、この価値は**既に実現済み**

| 項目 | 内容 | 評価 |

## ⑤ 3 案への推奨（oss-selfhost レンズから）

**推奨: 「両方」（ホスト提供の継続 + セルフホスト手段の整備）を段階的に。ただしセルフホストは"今すぐ大々的に推奨"ではなく"手順を整えて存在を示すに留める"**。

理由:
1. リポジトリ公開（論点③相当）は**既に完了した既成事実**であり、選択の対象ではない。今から議論すべきは「ホスト提供するか」と「フォークの障壁をどこまで下げるか」の 2 点
2. フォーク方式を**唯一の提供手段**にすると、①で洗い出した 25〜40 分・GitHub App 作成の鶏卵問題という参入障壁により、ミッション（思いついた瞬間を逃さない）に合致する新規利用者はほぼ生まれない。フォークで実際に使い始めるのは「読んで自分で解決できる開発者」に限られ、これはミッションの主要ペルソナ（PAT 管理が面倒な一般利用者）とは一致しない
3. 一方でホスト提供のみにして README にセルフホスト手段を一切示さないのは、コード監査可能性という信頼材料をみすみす捨てる。README に「セルフホストしたい方へ」のセクションと①の手順（鶏卵問題の回避手順込み）を用意するコストは低く、**将来「Deploy to Cloudflare ボタン設置」を Issue 化しておく価値はある**（ただし Workers Secrets プロンプトの実機検証が前提条件。②で述べた通り未検証のまま謳わない）
4. GitHub App の複製に伴う名称衝突リスク（③）を避けるため、README のセルフホスト手順に「GitHub App 名はフォーク時に variant 名へ変更すること」を明記する運用ルールを添える

**この議論の中で新たに見つけた別 Issue 化対象**（本セッションのスコープ外・CP-1 の解決規則に従い着手せず起票のみ推奨）:
- `content/pipeline-state/*` `content/analytics/*` のコスト実額データの公開露出（`.gitignore` 化 or 集計値の丸め検討）
- README への「セルフホスト手順」セクション追加（①のステップをそのまま転記可能）
- Deploy to Cloudflare ボタンの実機検証（Workers Secrets プロンプトが実際に出るかの確認）
- GitHub App 名称の fork 時変更ガイドラインの明記
