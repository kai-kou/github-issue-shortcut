## product-adoption 主張（Round 1）

### ① 公開の目的は「未定義」ではなく、実は既に確定済み — ただし「配布」と「集客」は別レイヤー

「今回一般公開すべきか」という問いは新規判断ではない。要件定義 §1.3（`docs/requirements/00-requirements.md:30`）が「**最初から一般公開を前提とし、誰でも GitHub ログインで利用できる**」と明記し、これは 2026-07-10 の基盤決定であり M1〜M3（54+20+21 SP）はすでにこの前提でドッグフーディング済み（`docs/requirements/04-milestones.md:78-86` の M1 Done 判定で「新規ユーザーがログイン→App インストール→初起票を 5 分以内に完了できる」を実機確認済み・2026-07-25・#95）。GitHub App も既に public 設定・説明文・プライバシーポリシー整備が完了している（brief (c)・#173 クローズ済み）。

したがって①②の問いは「一般公開するか」ではなく実質「**今から積極的に集客・告知するか**」である。誰に届けたいかはリーンキャンバス（`docs/requirements/01-lean-canvas.md:11,32`）で既に定義済み: 第一号は開発者自身、次いで「GitHub Issues で個人タスク管理する Android 使いの開発者（Zenn/Qiita 読者層）」。チャネルも `01-lean-canvas.md:14,55-57` で「GitHub 公開リポジトリ + 日本語技術記事」と決まっている。**この前提を今崩す動機は brief に見当たらない**。もし security-legal / ops-cost が「まだ届けたい相手が曖昧」と主張するなら、それは公開可否の論点ではなく、未着手の運用ガード（#171/#172/#179）の話にすり替わっている可能性がある。

### ② 3 案が KPI（初回セットアップ 5 分以内）に与える影響 — 定量評価

**現行のホスト提供モデル（GitHub OAuth・PAT レス）**: リーンキャンバス `01-lean-canvas.md:87` の通り「セットアップ 0 分（OAuth のみ）」が謳い文句であり、M1 Done 判定で実機 5 分以内を確認済み（`04-milestones.md:85`）。これは**既に達成・検証済みの資産**である。

**リポジトリのみ公開・各自フォーク方式（案③）を採った場合の推定所要時間**（`docs/requirements/00-requirements.md` 6 章のアーキテクチャ + `04-milestones.md` M0 タスクから逆算。実測ではなく合理的推定であることを明記する）:

**楽観合計（経験者・エラーなし）で約 30〜45 分、非技術者や初回 Cloudflare/GitHub App 利用者では 1〜2 時間超、離脱の可能性が高い。** これは KPI 目標（5 分以内）の **6〜24 倍以上** であり、目標の桁が違う。しかも「セットアップ」の定義（`project-mission.md:18` 初回セットアップ完了率＝ログイン→初起票 5 分以内）は「ログイン後」のみを指すが、フォーク方式ではその手前に「GitHub App 作成 + デプロイ」という**要件定義に存在しない新規工程**が挟まる。KPI の測定対象自体が変質してしまう。

**結論**: 案③（リポジトリのみ公開・セルフホスト必須）を「一般公開の唯一の手段」にすることは、ミッション KPI を事実上放棄する選択であり、リーンキャンバスの差別化要因そのもの（`01-lean-canvas.md:87`「セットアップ 0 分」）を自ら破壊する。案①（現行ホスト継続）が KPI 適合の唯一の現実解。

### ③ ドメインが体験・信頼に与える影響

OQ-7 は既に「workers.dev 継続・カスタムドメインは取得しない」と決定済み（`00-requirements.md:330`）。product-adoption の観点から再検討の必要性を検証したが、**覆す積極的理由はない**。

- PWA インストール後の体験（ホーム画面アイコン・スタンドアロン起動）では URL は表示されない。アプリ名は `vite.config.ts:66` で `"GitHub Issue Shortcut"` / short_name `"Issue Shortcut"` と設定済みで、これが利用者の目に触れる主要な識別子になる。URL の見た目が効くのは「初回ログイン前にアドレスバーを見る瞬間」と「GitHub 認可画面（GitHub 自身のドメインなので影響を受けない）」に限られる
- ターゲット層（`01-lean-canvas.md:32` Zenn/Qiita 読者層の開発者）は `*.workers.dev` を「個人開発 Cloudflare Workers アプリ」の記号として認識できる技術者であり、一般消費者向けサービスほど workers.dev サブドメインを不審に思わない。市場リサーチ（`docs/research/2026-07-10-market-competitors.md`）が示す通り、この製品はそもそも「実用ツール / OSS」（`01-lean-canvas.md:61`）であり信頼度が問われるのは「コードを検証できるか」（OSS 公開性）の方であって、ドメインの見た目ではない
- 唯一ドメインが効くのは M4（TWA / Play 配布）局面（Digital Asset Links の都合）だが、M4 は「実施判断保留」と既に決定済み（`04-milestones.md:15,168`）。今カスタムドメインを取得するのは、使うかどうか未定の将来オプションのために先出しコストを払うことになり、ミッションの YAGNI 判断基準（`project-mission.md:27`「まず自分が毎日使える最小構成。汎用化は後」）に反する

**結論**: ドメインは workers.dev 継続が妥当。再検討はカスタムドメインが必要になる具体的事象（TWA 着手判断）が発生してから。

### ④「今は公開しない/限定公開」という選択肢の評価

この選択肢には 2 つの読み方があり、混同を避ける必要がある。

- **読み方 A「一般公開の前提そのものを撤回し非公開に戻す」**: 支持しない。要件定義の基盤決定（§1.3）を覆し、M1〜M3 で実機検証済みの成果（54+20+21 SP）を無効化する重い decision であり、brief に新規のトリガー（重大インシデント等）は存在しない。ミッションの「まず自分が毎日使える」（`project-mission.md:27`）は既に満たされている（オーナー自身がドッグフーディング中）が、これは「非公開に戻す理由」ではなく「一般公開は既に前提として組み込まれている」ことの追認材料である
- **読み方 B「技術的には公開状態のまま、能動的な告知・集客だけ保留する」**: 支持する。現状は GitHub App が public 設定でも、Zenn/Qiita 記事等の能動的チャネル（`01-lean-canvas.md:14`）はまだ実行されていない。brief (c) に残る 3 件の未実装ガード（使用量アラート #171・アカウント保護手順 #172・サーバー側起票ガード #179）は、**運用が個人 1 人（brief (g)・オンコールなし）である以上、能動的な集客で流入が増える前に閉じておくべき前提条件**であり、product-adoption の視点からもこれに同意する。KPI 未達のまま人を呼び込むと「初見ユーザーが詰まって離脱する」体験の方がブランド毀損として重い（市場リサーチ `market-competitors.md:12` の Anywhere Issue「連携後リポジトリが出ない」致命的レビュー事例が反面教師）

**推奨**: 「公開するかどうか」の二択ではなく、「技術的公開（既に完了）」と「能動的告知（#171/#172/#179 クローズが前提条件）」を分離した段階公開が KPI・持続運用の両面で最も合理的。

### ⑤ 他レンズ（セキュリティ・コスト）の慎重論への反論

security-legal / ops-cost が「リスク・コスト面から公開を遅らせる、またはセルフホスト方式に倒すべき」と主張してきた場合を想定した反論:

- **「セルフホストにすればリスク・運用負荷が減る」への反論**: 案③はオーナーの運用責任を軽減しない。各フォーカーが自分の GitHub App・Cloudflare アカウントを作る以上、悪用対策（PR-4/PR-5）・鍵管理・監視は各自が個別に（多くの場合本家より低い品質で）再実装することになり、**製品としての事故は減らず、むしろ「本家より緩い設定の乱立」という新しい低品質サーフェスを生む**。セキュリティ上の余caution は「案③への逃避」ではなく「案①のまま #171/#172/#179 を閉じる」ことで対応すべきで、これは KPI を犠牲にしない解
- **「コストが心配なら公開を遅らせるべき」への反論**: brief (b) の通り無料枠のまま数千 DAU まで耐える試算があり、かつ D1 撤去後はさらに余裕がある。市場リサーチ（`market-competitors.md:44-47`）は市場規模自体が小さいこと（競合 3 アプリの評価件数が各 3 件程度）を示しており、急激なコスト超過シナリオの蓋然性は低い。コスト慎重論は「使用量アラート（#171）を先に付ける」で十分吸収でき、公開可否や配布方式の変更を要する規模の懸念ではない
- 総括: セキュリティ・コストどちらの慎重論も「案③への転換」や「一般公開の撤回」を正当化する強さはなく、せいぜい「#171/#172/#179 を能動集客の前提条件にする」（④の推奨と一致）レベルの手当てで足りる

### ① 現本番（workers.dev）をそのまま一般公開

**残存リスク（過大評価せず）**

1. **トークン中継者としての責任は「軽量化されたが消えていない」**（`data-retention-inventory.md` §2.2）。Worker は `/api/*` で毎リクエスト Cookie を復号し平文トークンをメモリ上で扱う。保持ゼロでも **処理中の露出面** は残る（漏洩の一撃性は下がったが、Worker 実行環境自体の侵害・依存パッケージの sc攻撃には無防御）。鍵ローテーション時に旧鍵の Cookie は復号不能→再ログインで済む設計（`worker/crypto.ts` の `sealVersioned`/`openVersioned`）は良い緩和だが、**鍵漏洩そのものを検知する手段（異常アクセス監視）は #172 待ち**（brief (c)）。
2. **GitHub App 単一障害点は解消されていない**（旧 R5）。`docs/requirements/00-requirements.md` PR-5（422 連発ユーザーの自動抑止）は SHOULD のまま未実装（brief (c) の #179 = 「サーバー側の起票ガード」が該当）。1 ユーザーのスパム起票で App が停止すれば **全利用者が同時に使えなくなる**（トークンを預からない設計でも、GitHub 側の信頼点は 1 つのまま）。GitHub 公式には「abuse detection で App/アカウントが自動制裁される」実例が多数あるが（[GitHub Community #191078](https://github.com/orgs/community/discussions/191078) 等）、「1 App = 全ユーザー停止」の公式ポリシー文書は見当たらず、**リスクの実在は合理的推定（レート制限 PR-4 は実装済みだが日次上限なし）** であり確度は「中」と評価する。
3. **workers.dev はゾーン機能（WAF・Rate Limiting Rules・Turnstile）を使えない**という前提（旧 R6）は Cloudflare 公式ドキュメントで明示的に「WAF 非対応」と書かれた一次情報は見つからなかった（[workers.dev routing docs](https://developers.cloudflare.com/workers/configuration/routing/workers-dev/) は「Free website として個人・趣味用途を想定」としか書いていない）。ただし Turnstile・WAF・Bot Management は Cloudflare の「ゾーン」単位機能であり、workers.dev はゾーンを持たない仕様上の帰結として使えないというのが実務上の共通認識（`2026-07-27-public-release-risk-cost.md` R6 の記述と整合）。**確度は「高いが一次情報での断定はできない」** としておく。実害は「未認証フラッドでもリクエスト数を消費する」点で、アプリ層レート制限（GitHub 認証必須・401 早期リターン）はあるが、無料枠の日次上限そのものには当たりうる。**#171（使用量アラート）が未実装のままだと「気づいたら止まっていた」が起きる**。
4. **法務面の残存 1 点（見落としやすい）**: `src/i18n/translations.ts` のプライバシーポリシー（7 節構成・P4 で更新済み）を確認したところ、**問い合わせ窓口（7 節）・保持期間（4 節）・基盤側記録（5 節）は明記済み**で `2026-07-27-public-release-risk-cost.md` R7 の当時の指摘は大半解消されている。しかし **Cloudflare が米国事業者であること・データが越境処理されることの明記が一切ない**（`米国`/`海外`/`アメリカ` で grep して 0 件）。個人情報保護委員会のガイドライン（[外国にある第三者への提供編](https://www.ppc.go.jp/personalinfo/legal/guidelines_offshore/)）では、外国にある事業者を「委託先」として使う場合（第三者提供ではなく委託）でも、**「外的環境の把握」として委託先が所在する外国の名称と当該国の個人情報保護制度の情報提供が求められる**（令和 4 年改正 Q&A）。本アプリは Cloudflare を委託先として使っている（トークンの独立利用はさせていない）ため 28 条の本人同意までは不要と整理できるが、**「外的環境の把握」の情報提供は別途必要**。ここは `docs/research/2026-07-27-public-release-risk-cost.md` §4 の「越境移転」論点がまだプライバシーポリシー本文に反映されていない、という **具体的な未了タスク**として指摘する（ファイル: `src/i18n/translations.ts` 2 節 or 新設 8 節に「Cloudflare（米国に本社を置く事業者）のインフラを利用しており、処理は日本国外でも行われうる」旨を追記）。

**評価**: 技術的な公開ブロッカーはない（brief (c) の通り GitHub App public 化・権限説明・PP/ToS 整備は完了済み）。残るのは **文書 1 点の追記** と **#171/#172/#179 の実装状況の確認**。「公開してよいか」は Yes、「無条件で今すぐ」は No（下記②の条件を満たしてから）。

### ② リポジトリのみ公開してセルフホスト方式

**セキュリティ・法務上の責任がどう動くか（本質的な比較軸）**

- **トークン中継者の責任が消える**: 各自が自分の GitHub App（またはOAuth App）を登録し、自分の Cloudflare アカウントにデプロイするため、**運営者（オーナー）は他人の GitHub トークンに一切触れない**。これは「持つことで発生する責任」（`2026-07-27-public-release-risk-cost.md` §2）を構造的にゼロにする、保持ゼロ化よりさらに一段強い解決。
- **法務責任も利用者ごとに分散する**: APPI・GDPR の「個人情報取扱事業者」はフォークして自分のインフラにデプロイした本人になる。オーナーは「コードの作者」であり「サービスの運営者」ではなくなるため、PR-1〜PR-3（利用規約・プライバシーポリシー・アカウント削除案内）はオーナー自身のサービスとしては不要になる（各自が必要なら自分で書く）。ただし **オープンソースの提供者としての一般的な免責（無保証条項・MIT 等ライセンスの Disclaimer）は引き続き必要**（`docs/requirements/00-requirements.md` PR-1 の思想を README/LICENSE に落とす形に付け替え）。
- **GitHub App 単一障害点も分散する**: 各自が自分の App を登録するため、1 人のスパムが全利用者に波及するリスクが消える（旧 R5 の根本解消）。
- **セルフホストの実務ハードルが新たなリスクに転化する**: `TOKEN_ENCRYPTION_KEY` の生成・Secrets 登録・OAuth App の Callback URL 設定など、セキュリティ設定を利用者自身が正しく行える保証がない。**誤設定（例: `TOKEN_ENCRYPTION_KEY` を弱い値にする、workers.dev の URL を推測されやすい命名にする）のリスクは利用者に転嫁されるだけで消えない**。README にセキュリティ設定のチェックリストを用意しないと「フォークしたら Client Secret が漏れた」を運営者が防げなくなる（ただし責任も転嫁されるので、オーナーにとってのリスクではなく利用者にとってのリスク）。
- ミッション KPI「初回セットアップ 5 分以内」（brief (f)）との衝突: GitHub App 登録・Secrets 設定・`wrangler deploy` を要求するセルフホストは、非エンジニアには 5 分で終わらない。**①（ホスト提供）はこの KPI を満たすが、③（セルフホストのみ）は満たさない**。ここは他レンズ（プロダクト側）と評価が割れる可能性がある。

### ③ 両方（ホスト版を運営しつつリポジトリも公開）

### ドメイン方針への意見

**workers.dev 継続を支持する（現時点ではカスタムドメイン取得は不要）**。根拠:

- OQ-7 は 2026-07-10 に決定済みで覆す新情報がない。`__Host-` Cookie 属性はホスト単位でありサブドメインでも安全性は変わらない（`docs/design/stateless-architecture.md` §4）。
- カスタムドメイン化の主目的は WAF/Turnstile 導入（旧 R6 の本格対応）だが、これは「無料枠のまま数千 DAU」の規模では過剰投資。保持ゼロ化でトークンを預かる期間がリクエスト処理中だけになった今、**エッジ防御の欠如は「なりすまし」ではなく「リソース消費・可用性」のリスクに性質が変わっている**（トークンは既に暗号化 Cookie 側にあり、WAF はそれを守るものではない）。であれば #171（使用量アラート）で十分にカバーできる。
- **カスタムドメイン化を「今回のトリガー」にすべき条件を明記**: TWA 化（M4）でアプリ的信頼性向上が必要になったとき、または実際に workers.dev の無料枠制限（Workers リクエスト 10 万/日）に到達が見えてきたとき。それまでは「ドメイン変更」という不可逆コスト（OAuth callback URL 変更・GitHub App 設定変更・利用者のブックマーク切れ）を払う理由がない。

### 他レンズが言いそうな楽観論への先制反論

- **「保持ゼロ化したのでリスクは実質ゼロ」への反論**: 保持ゼロは「盗まれたときの被害の永続性・鍵ローテーション不能」という**静的リスク**を消したのであって、**処理中の一時露出**（Worker 実行環境の侵害・依存パッケージの脆弱性）と**GitHub App 単一障害点**という**動的リスク**は別物で消えていない。R1/R2 は「軽量化」であって「解消」ではない（`data-retention-inventory.md` は D1 撤去の事実を述べているが、Worker が「復号→GitHub 呼び出し→破棄」する構造自体は残ると明記・§2.2）。
- **「GitHub App が public 設定・権限整備済みだからもう公開できる」への反論**: PR-6（App 設定）の完了は **入口の要件**であって、PR-5（スパム自動抑止）が SHOULD のまま未実装（#179）なのは **出口の要件**が空いたまま。1 ユーザーの悪用で App 全体が止まるシナリオは PR-4（レート制限）だけでは防げない（日次上限がないため「1 分 10 件を 24 時間回し続ける」= 14,400 件/日は技術的に可能）。
- **「個人開発・無償提供だから法務は最低限でよい」への反論**: 無償・個人開発であっても、EU 圏の利用者が使えば GDPR の管理者責任は発生し（brief に地域制限の言及なし＝グローバルに開放される前提）、APPI も事業規模を理由に適用除外にはならない（個人情報保護法に小規模事業者の適用除外規定はない。2015 年改正で撤廃済み）。「問い合わせ窓口すらない」状態は個人開発でも最低限の実務違反になりうる、という点は本アプリでは **P4 で既に手当て済み**（7 節）なので実害はないが、「無償だから何もしなくていい」という一般化には同意しない。
- **「workers.dev のままでも実害はない」への反論**: 現時点の DAU 規模では正しいが、brief (b) の「無料枠のまま数千 DAU」試算は **D1 時代の書き込みボトルネック前提**であり、D1 撤去後の実際のボトルネックは Workers リクエスト数（10 万/日）に一本化されている。ここへの到達可能性（未認証フラッド含む）を監視する #171 が未実装のまま「実害はない」と言い切るのは、**観測手段がないのに安全と主張している**状態であり、公開前に埋めるべき条件からは外せない。

## ④ 監視未設定（#171）で起きる失敗シナリオ（数値付き）

1. **無料枠の Requests 上限到達で「静かな全停止」**: Workers Free プランは 100,000 requests/日を超えると **Error 1027** を返し、**00:00 UTC（09:00 JST）のリセットまで完全復旧しない**（2026-07-28 WebSearch 確認）。現在の DAU 換算天井は約 6,600（§②）。使用量アラート・予算ガード未実装（`docs/requirements/00-requirements.md` 191 行目 NFR-14 の「枠超過が近づいたら検知できること」が未達）のため、**運営者はアプリが落ちていることに利用者からの申告以外で気づく手段がない**。一人運用（brief (g)）のため、気づくのが翌朝以降になる想定は十分あり得る。
2. **想定される到達経路は「成功」と「攻撃」の両方**: 6,600 DAU は決して極端な数字ではない（Twitter/X 等での紹介 1 回でも短時間の急増はあり得る）。逆に、workers.dev には WAF が無いため（§③）、**未認証フラッドが Requests 枠だけを消費して同じ Error 1027 を引き起こせる**（`docs/research/2026-07-27-public-release-risk-cost.md` R6 行・93 行目「未認証フラッドでも **リクエスト数は消費する**」と整合）。つまり悪意の有無に関わらず同じ壊れ方をする。
3. **復旧確認の手段もない**: Analytics Engine 等の計測バインディングは未導入（`docs/research/2026-07-27-public-release-risk-cost.md` 21 行目）。ダッシュボードを能動的に見に行かない限り、リセット後に正常化したかどうかも分からない。
4. **数値的インパクト**: 全停止時間の期待値は「検知手段ゼロ」を仮定すると 0〜24 時間（発生タイミングと運営者の生活サイクル依存）。ミッション KPI（初回セットアップ 5 分・起票 10 秒）の観点では、**新規ユーザーの初回体験がまさにこの停止時間帯に当たった場合、離脱コストが最大化する**（初見で使えないアプリは再訪されない）。

**対策コストは実質ゼロ**: Cloudflare の使用量アラート（Notifications）自体は無料枠でも設定可能で、実装コストは低い（#171 が既に Issue化 済み）。ここは「コストが天井」ではなく「未実装であること」が問題であり、公開前提条件として費用対効果が最も高い項目。

| コストの帰属 | 運営者 1 人に集中（ただし §①②の通り極小: 無料〜$5/月で数万 DAU まで対応） | **利用者ごとに分散**（1 人あたり自分の無料枠内で収まる規模が確実なので、事実上ほぼ全員 $0） | 集中と分散が並存。ホスト版の運用負荷は減らない |
| 監視・可用性責任 | 運営者 1 人が全利用者分の可用性に責任（§④のリスクが全利用者に波及） | 各利用者が自分の分だけに責任（障害の影響範囲が利用者 1 人に限定される・**責任分散という設計上の利点**） | ホスト版利用者は①と同じ集中リスクを負う |
| 追加で必要な運用作業 | 使用量アラート設定・アカウント保護（#172）・起票ガード（#179） の 3 件（費用ほぼゼロ・工数小、§④） | 運営者側の追加運用作業は **ほぼゼロ**（GitHub App 新規作成・Secrets 設定などはすべて利用者側作業。ただしこれはコストではなく普及面の負荷なので oss-selfhost/product-adoption の担当領域） | ①の作業に加えて何もしなくてよい（②相当の分は利用者に転嫁されるため運営者コスト増にはならない） |
| コスト構造上の懸念点 | **無い**（§①②の通り、数千〜数万 DAU まで実額コストは軽微） | 運営者コストの懸念は無い（そもそも運営者のインフラを使わない） | 運営者コストの懸念は①と同じで無い |

**ops-cost レンズからの一言**: 3 案のどれを選んでも、**Cloudflare の実額コストが意思決定のボトルネックになることは無い**（D1 撤去後は特に）。差がつくのは「可用性の責任がどこに集中するか」であり、これは費用の問題ではなく §④ の監視体制の問題に帰着する。したがって ops-cost の立場からは、**host-only の実行可否はコストではなく #171（使用量アラート）の実装有無で判断すべき**、という点を強調したい。

## ② 自動化できる範囲 / できない範囲

一次情報: [Deploy to Cloudflare buttons](https://developers.cloudflare.com/workers/platform/deploy-buttons/)、[2025-04-08 changelog](https://developers.cloudflare.com/changelog/post/2025-04-08-deploy-to-cloudflare-button/)、[GitHub App manifest flow](https://docs.github.com/en/apps/sharing-github-apps/registering-a-github-app-from-a-manifest)（WebSearch/WebFetch で確認済み・2026-07-28 時点）。

| 領域 | 自動化可否 | 詳細 |
|------|----------|------|
| リポジトリの Fork/複製 | ✅ 自動 | Deploy to Cloudflare ボタンが「利用者の GitHub/GitLab アカウントへ複製」を実行 |
| Cloudflare リソースのプロビジョニング（KV/D1/R2/DO） | ✅ 自動（ただし**本アプリは対象外**） | `stateless-architecture.md`（P4・#166）で D1 を含む永続層を全廃済みのため、そもそもプロビジョニング対象が無い。これは**フォーク障壁を実質下げている**ポジティブな事実（以前の D1 時代なら DB マイグレーション適用が追加の手作業だった） |
| Workers Builds の Git 連携（CI/CD 配線） | ✅ 自動 | ボタン経由なら配線込みでデプロイまで完了 |
| `vars`（`GITHUB_CLIENT_ID` 等の非秘匿値） | ✅ 自動（プロンプト入力） | Cloudflare 側ドキュメントは `wrangler.jsonc` の `vars` をデプロイ時に自動処理すると説明 |
| Workers Secrets（`GITHUB_CLIENT_SECRET` / `TOKEN_ENCRYPTION_KEY`） | 🟡 **部分自動（要検証）** | ドキュメントは「`.dev.vars.example` / `.env.example` の dotenv 形式で secrets を定義でき、デプロイ時に値入力を促せる」と説明するが、プロンプト UI が確実に出るかは一次情報だけでは断定できない（要実機確認）。本リポジトリは `REPO/.dev.vars.example` を既にその形式で持っているため、**ボタンを追加する実装コストは小さい可能性が高い**が、動作検証なしに「自動化済み」と謳うのは時期尚早 |
| **GitHub App の新規作成そのもの** | ❌ 自動化不可（Cloudflare の管轄外） | Cloudflare は GitHub Apps/OAuth Apps の作成に一切関与しない。GitHub 側の Manifest flow（利用者を `github.com/settings/apps/new` へ POST 遷移させ、事前入力済みの App 作成画面を出す）は**入力の事前充填**はできるが、**「Create GitHub App」ボタンをユーザー本人が手でクリックする最終確認は省略できない**（GitHub 側の意図的なセキュリティ設計）。さらに Manifest flow を使うには、コールバックで返る一時 `code` を `POST /app-manifests/{code}/conversions` に交換する**受け皿サーバーを自分で用意して運用する必要がある**（本プロジェクトが新たに実装・保守すべき追加コンポーネント） |
| **Callback URL の鶏卵問題（①手順 3/9）** | ❌ 自動化不可 | Worker の実 URL が確定する前に GitHub App を完成させられないという順序制約は、ボタン化しても消えない構造的な問題 |

**結論**: 「ワンクリックで完全セルフホスト」は実現できない。Cloudflare 側（ホスティング）は Deploy ボタンでほぼ自動化できるが、**GitHub App 作成という GitHub 側の手作業が必ず残る**。これは実装で埋められない領域であり、README に「① ボタンを押す ② GitHub App を作る（手順書リンク）③ URL 発行後に Callback URL を直す」という **2 段階ガイド**として明示するのが現実的な最善。

## ③ フォーク方式の隠れコスト

- **サポート issue の流入**: 「ログインできない」「起票が失敗する」系の issue は、実際には利用者自身の GitHub App 設定ミス（Callback URL 不一致・Permissions 不足）であることが大半になる想定だが、issue 起票者にはオーナー本体の不具合と見分けがつかない。オーナーは他人の Cloudflare/GitHub App 設定を覗けないため**再現も遠隔デバッグもできず**、`/health` 的な自己診断（①手順 10）を案内する以上のことがしづらい
- **環境差分のデバッグ**: `wrangler.jsonc` の `ratelimits`（`REPO/wrangler.jsonc:28-45`）・`observability`（同 46-58）はフォーク先でも同じ値が引き継がれるが、フォーク先のトラフィック傾向次第では意味を持たない設定になりうる（例: 無料プランの Rate Limiting binding 上限、Workers Paid 未契約なら observability retention が 3 日固定 — `stateless-architecture.md:151`）。「なぜ自分の環境では挙動が違うのか」の切り分けコストは fork 側・本家側の双方に発生する
- **アップストリーム追随**: フォークは `git fetch upstream` を能動的に回さない限り更新が来ない。特にセキュリティ修正（例: 将来 `TOKEN_ENCRYPTION_KEY` の取り扱いに脆弱性が見つかった場合）が**フォーク先には自動で届かない**。Dependabot（`REPO/.github/dependabot.yml` 確認済み）は依存パッケージの更新は検知するが、本体コードの修正までは検知しない
- **複製 App による GitHub 側の混乱**: 各フォーカーが独自の GitHub App を作る設計自体は問題ないが、命名を "GitHub Issue Shortcut" のまま複数人が使うと、GitHub の認可画面（"〇〇 by 開発者名 wants to access your account"）でユーザーが本家と別物であることに気づきにくい。名称ガイドラインで「フォーク時は別名にする」を明示しないと、本家の評判に対する取り違えリスクがある
- **脆弱な設定が本家の評判に返る**: フォーク先が `TOKEN_ENCRYPTION_KEY` を弱い値のまま使う・Permissions を過剰に広げる等をした場合の実害は当人限定だが、「GitHub Issue Shortcut で被害が出た」という形で言及されるリスクはゼロではない（README 免責文言・SECURITY.md の対象外明記で軽減可能。`REPO/SECURITY.md:16-19` は既に依存脆弱性を対象外にしているが、フォーク先の設定不備は明記されていない）

## ⑤ 3 案への推奨（oss-selfhost レンズから）

**推奨: 「両方」（ホスト提供の継続 + セルフホスト手段の整備）を段階的に。ただしセルフホストは"今すぐ大々的に推奨"ではなく"手順を整えて存在を示すに留める"**。

理由:
1. リポジトリ公開（論点③相当）は**既に完了した既成事実**であり、選択の対象ではない。今から議論すべきは「ホスト提供するか」と「フォークの障壁をどこまで下げるか」の 2 点
2. フォーク方式を**唯一の提供手段**にすると、①で洗い出した 25〜40 分・GitHub App 作成の鶏卵問題という参入障壁により、ミッション（思いついた瞬間を逃さない）に合致する新規利用者はほぼ生まれない。フォークで実際に使い始めるのは「読んで自分で解決できる開発者」に限られ、これはミッションの主要ペルソナ（PAT 管理が面倒な一般利用者）とは一致しない
3. 一方でホスト提供のみにして README にセルフホスト手段を一切示さないのは、コード監査可能性という信頼材料をみすみす捨てる。README に「セルフホストしたい方へ」のセクションと①の手順（鶏卵問題の回避手順込み）を用意するコストは低く、**将来「Deploy to Cloudflare ボタン設置」を Issue 化しておく価値はある**（ただし Workers Secrets プロンプトの実機検証が前提条件。②で述べた通り未検証のまま謳わない）
4. GitHub App の複製に伴う名称衝突リスク（③）を避けるため、README のセルフホスト手順に「GitHub App 名はフォーク時に variant 名へ変更すること」を明記する運用ルールを添える

**この議論の中で新たに見つけた別 Issue 化対象**（本セッションのスコープ外・CP-1 の解決規則に従い着手せず起票のみ推奨）:
- `content/pipeline-state/*` `content/analytics/*` のコスト実額データの公開露出（`.gitignore` 化 or 集計値の丸め検討）
- README への「セルフホスト手順」セクション追加（①のステップをそのまま転記可能）
- Deploy to Cloudflare ボタンの実機検証（Workers Secrets プロンプトが実際に出るかの確認）
- GitHub App 名称の fork 時変更ガイドラインの明記
