## ⑤ 5 秒 KPI の自動化形態（定量的懸念）

提案で「5 秒 KPI を assert に強める」案に対する懸念:

```
kpi.spec.ts の現在の立場（コメント抜粋）:
  ✅「アプリ処理が遅くなっていないか」の監視（回帰ガード）
  ❌「WebAPK/standalone のコールドスタート・実機ソフトキーボード遅延・
      CPU throttling といった実機体感は含まない」
  ❌ 本 spec の合否は NFR-2 の実機 10 秒基準の代替ではない

threshold assert 強化の問題:
- 環境 variance（CI マシン性能・GC タイミング）により
  「本当は実機で 4.5 秒」でも「CI エミュレーション上で 5.2 秒」の可能性
- 「E2E が 5.1 秒だから本番は OK」という誤認を招く
- 実際の 5 秒基準は「実機での体感計測」が本来のプロフ値であるべき
```

**推奨**:
- 5 秒基準は「参考値」のまま（assert 強化しない）
- 本当の KPI（NFR-2）は定期的な実機計測で監視（別プロセス）
- E2E は「回帰（= 前回より遅くなった）」検知に限定

→ 自動化の過度な信頼は危険。定期実機測定の方が安い。

### ③ 追加すべきでない（重複になる）項目とその理由

## real-device-realist: 機構レベルの不可能性分析（round 1）

前提確認: `playwright.config.ts` の `...devices["Pixel 7"]` は **Chromium デスクトッププロセスに viewport/UA/DPR/touch フラグを与える記述子** であり、実 Android Chrome バイナリでも実 OS でもない。ここが全指摘の土台。

### ① エミュレーション不可能な項目と機構的理由

**(A) 項目 4 の「候補タップでキーボードが閉じない」（`src/issues/IssueForm.tsx:205-213`）**

実装は `onMouseDown={(e) => e.preventDefault()}` → `onClick={() => applySuggestion(name)}`。コメント通り「タップで入力欄からフォーカスが外れるとソフトキーボードが閉じてしまうため」の対策。Playwright の `.click()` は CDP `Input.dispatchMouseEvent` で `mousedown`→`mouseup`→`click` を合成発火するので、**DOM 上の `preventDefault` 実行と `document.activeElement` が input に留まること自体は検証できる**（実際 `smart-input.spec.ts:87` の `toHaveValue` 通過はこれを暗黙に裏付けている）。

しかし「キーボードが閉じない」の実体は **OS の `InputMethodManager` が別プロセスの IME（Gboard 等）に対して表示継続を指示するか** という OS レベルの状態遷移であり、DOM フォーカス保持とは別物である。Headless Chromium には `InputMethodManager` へのバインダー接続も、レンダリングすべき仮想キーボードパネルも存在しない（IME プロセス自体が起動しない）。したがって Playwright は「フォーカスを失わないコードパスを通ったか」までしか検証できず、「実機で本当にキーボードパネルが画面に残り続けるか」は原理的に検証不能。DOM 状態とレンダリングされた IME パネルの表示状態は別レイヤーの現象であり、前者の green は後者を保証しない（偽陰性の温床）。

**(B) `interactive-widget=resizes-content`（index.html:5）と viewport のリサイズ挙動**

このメタ属性は実 IME キーボード出現時に visual viewport がどう縮む/コンテンツがどうリサイズされるかを制御する。Headless Chromium にはキーボードパネルのオーバーレイ自体が存在しないため `window.visualViewport.height` がキーボード分だけ縮む実映像は再現されない。つまり「候補チップがキーボードの上に隠れず見えている」「入力欄がキーボードに覆われず見える」というレイアウト崩れ検知は、そもそも縮む対象（実キーボード）がないので検証不能。

**(C) WebAPK standalone コールドスタート（項目 7・5 秒 KPI）**

`kpi.spec.ts` 自身のコメント（L8-17）が既に明記: 計測できるのは「アプリが理論上出せる下限値」のみ。実機コールドスタートは ① Android パッケージマネージャによる WebAPK（署名済みネイティブシェル）プロセス生成 ② Chrome レンダラプロセスの cold spawn（CI では既に温まった V8 isolate を使い回す） ③ Service Worker の初回 activate（`vite-plugin-pwa` 系の SW 登録・キャッシュヒット判定） ④ 中〜低位機の CPU/thermal throttling、という CI ヘッドレスには存在しない待ち時間を含む。`page.goto()` は「既に起動済みブラウザに新規タブでナビゲートする」だけで、OS のアプリ起動（プロセス生成・binder IPC）を一切経由しない。5 秒 KPI（NFR-2）の実測値は、この cold-start コストがゼロの環境で測った値であり、実機の合否判定にはなり得ない。

**(D) Service Worker Background Sync（オフライン再送）**

`offline-queue.spec.ts` 自身のコメント（L9-10）が明記: Workbox の Background Sync（ページを閉じていても再送）はテスト対象外。現行テストは `page.route(...).abort()` でネットワーク層をアプリ内 fetch 単位で失敗させ、復帰は `page.evaluate(() => window.dispatchEvent(new Event("online")))` で **フォアグラウンドの `online` リスナーを直接叩いている**。これは SW の実際の `sync` イベント（ブラウザのネットワーク変化検出が SW を起こして発火する、タブが閉じていても発生しうるイベント）とは別の経路。Background Sync の本来の価値（タブを閉じていても再送される）は、ページが存在し JS が実行できることを前提にした `page.evaluate` では原理的に検証できない——タブを閉じた状態を作った瞬間 Playwright の実行コンテキストそのものが失われるため。

**(E) 実指タップ精度・実機フォント視認性**

Playwright の合成タップは単一座標への理想的なヒットであり、コンタクト楕円・指の accidental slip・隣接要素（ラベルチップ `smart-token-chips` とチェックボックス群）への誤タップは再現されない。フォント視認性（屋外光下でのラベルチップの色コントラスト等）も、ヘッドレス Chromium の仮想フレームバッファは物理ディスプレイパネル・輝度・反射・DPI 実測値を持たないため、スクリーンショット diff では担保できない知覚的品質。
