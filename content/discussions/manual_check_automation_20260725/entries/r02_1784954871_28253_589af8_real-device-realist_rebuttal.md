## real-device-realist: round 2 rebuttal / concession

### 対 automation-maximalist（②の機械化代替案の是非を機構レベルで再判定）

**明示的に譲歩する代替案（等価ではないが正当な回帰プロキシとして追加を支持）**:
- **P1-1（`toBeFocused()` 追加）**: 支持する。これは「実機でキーボードが閉じない」の証明にはならない（自分の round1 (A) と同じ限界）が、`IssueForm.tsx:209` の `onMouseDown preventDefault` という **既に一度必要になった実装** の回帰プロキシとして正当。ただし docstring/コメントに「これは DOM フォーカス保持の検証であり、実機 IME パネルの表示継続の証明ではない」と明記することを条件に付ける（yagni-guard が懸念する「誤った安心感」の防止）。
- **P1-2（mock issue-count カウンタ + re-entrancy 回帰テスト）**: 支持する。ただし後述の通り、私の round1 での重複懸念は automation-maximalist の指摘で **実は大幅に緩和される**（下記「譲歩」参照）。
- **P1-3（`dist/sw.js` の Background Sync config grep）**: 支持する。これは「SW が実際に発火するか」ではなく「設定が存在し続けるか」という別種の回帰であり、実機必須の主張と矛盾しない。安価で正しい切り分け。

**却下を追認する（automation-maximalist が自ら切り捨てた案に、機構的理由を補強する）**:
- **`visualViewport` assert**: 却下に同意。理由を補強すると、これは単なる「費用対効果ゼロ」ではなく **構造的にテートロジー**（＝いかなる実装破壊でも検知不能）。Headless Chromium は実 IME オーバーレイを持たないため `visualViewport.height` はフォーカス状態と無関係に不変であり、「常に green」を返し続ける。これは round1 (B) の主張と同一機構であり、追加するとテストスイートに **偽の安全信号** を恒久的に埋め込むことになる（yagni-guard の「誤認を招く」という懸念と完全に一致）。
- **CDP 生キーイベント / display-mode:standalone スタブ**: 却下に同意。grep 結果（候補確定は click のみ、`display-mode:standalone` 分岐コードはアプリに存在しない）を信頼する限り、これらは「存在しないコードパスを踏むための道具」であり、追加コストに見合う新規シグナルがゼロ。
- **SW 単体テスト（fake-indexeddb で `sync` を合成発火）**: 却下に同意。ここが本質的な論点: 合成発火した `sync` イベントは「JS がそのイベントハンドラを正しく実行するか」しか検証できず、**OS が実際にそのイベントをいつ・どの条件で発火するか**（Android の Doze/App Standby バケット・バッテリーセーバー・ネットワーク種別変更の検出タイミング）という契約側は一切模造できない。「ハンドラが正しい」と「OS がハンドラを呼んでくれる」は独立した2つの信頼性要件であり、fake-indexeddb は前者しか触れない。

**automation-maximalist に対する明示的な譲歩（私の round1 の主張を修正する）**:
`worker/store.ts:75-77,312-333` を確認した。`request_ids` テーブルは `PRIMARY KEY (user_id, client_request_id)` + `ON CONFLICT DO UPDATE` で、クライアント/SW どちらの経路が起票 API を叩いても **同一 `client_request_id` である限りサーバー側で構造的に重複が collapse する**（`issue_log` の `content_hash` + 時間窓による二重防止と二段構え）。これは automation-maximalist の「自動化ギャップ＝安全性ギャップではない」という評価が **事実として正しい** ことを裏付ける。したがって round1 で私が「重複なし」をオフライン系の実機必須項目に含めた（チェックリスト項目 3）のは **過剰** だった。**修正**: 「重複なし」はサーバー側の冪等性キーで担保済みのため実機確認から外してよい。実機で本当に確認すべきは「タブを閉じた状態から **自動再送が実際に起動するか**」という発火可否のみ（重複の有無ではなく、再送そのものの発生有無）。

### 対 e2e-coverage-auditor（「✅ カバー済み」判定に潜む偽陰性）

判定表①・③の「重複コストのみで新規シグナルなし」という評価は状態遷移ロジックに限れば正しい。しかし ✅ 判定された項目にも **実機性の観点での残余リスク** がある。auditor 自身が項目1の脚注で認めている通り「ハイライト＝視覚スタイルは未検証」だが、これはより広い問題の一例に過ぎない:

- **項目1・3・6の共通の偽陰性**: `getByRole("button", { name: ... })` によるクリックは **意味的（アクセシビリティツリー）にターゲットへ完璧に命中する合成イベント**。実指のタップは接触楕円を持ち、`smart-token-chips`（チップ群）や `ラベル候補` リストのように **視覚的に近接した複数のタップ可能要素** がある画面では、意図した要素の隣を叩いて別の要素が反応する「誤タップで別の意味論的操作が起きる」ケースを検出できない。これは「ロジックが正しいか」ではなく「実機の指で正しい要素に到達できるか」という別レイヤーの正しさであり、role ベースのテストが green でも実機で誤操作が起きうる（round1 (E) と同型）。
- **項目6（チップ解除）の偽陰性**: チップとラベル候補チップの視覚的密度が高い場合、8px 未満の実効タップ間隔（design-guidelines D-6? — 実測要）が生じていないか。テストは論理的な `.click()` 成功のみを見ており、実機での **タップ target のジオメトリ的な妥当性**（8px 以上の間隔があるか）は座標ベースの実機検証でしか担保できない。
- **総括**: auditor の判定は「機能ロジックが動くか」の軸では正確だが、「実機の指がその機能に正しく到達できるか」の軸は範囲外であり、この軸の偽陰性リスクは round1 の手動チェックリスト項目4（実指タップ精度）でカバーする以外に手段がない。auditor の対応表に「ロジックカバー済み」と「実機タップ幾何がカバー済み」を混同しないよう明記すべき。

### 対 yagni-guard（却下判断が実機で壊れるリスクを見落としていないか）

機構レベルの主張（③④）には同意する: **実機テストの完全代替は不可能** という一次主張は正しく、私の round1 と同一結論。しかし yagni-guard の却下範囲が広すぎる。

- **見落とし1: 「代替不可能」と「回帰プロキシとして無価値」を混同している**。`toBeFocused()`（P1-1）は「実機でキーボードが閉じるか」の代替では **ない** が、`IssueForm.tsx:209` の `onMouseDown preventDefault` という **過去に実際に必要になった実装**（コード中のコメントが明記）に対する最小コストの回帰ガードである。yagni-guard の論拠④「完了済み Issue のかつての手動確認を再現するテストは1回限りコスト」は誤りで、これは「過去の手動確認の再現」ではなく「過去に修正した実装が将来のリファクタで壊れないことの検知」であり、性質が異なる。この1行を却下すると、次に誰かが候補ボタンの `onMouseDown` を触った際、CI は何も検知せず、**次の実機確認（マイルストーンゲートのみ）まで壊れたまま気づかれない**——まさに yagni-guard 自身が④で懸念する「かつての確認の形骸化」を、テストを削ることで逆に招き入れている。
- **見落とし2: P1-3（SW config grep）も同じ理屈で棄却しているが、これは新規ライブラリ・新規重量級ツールではない**。yagni-guard の③（D-6 違反リスク）は allure-playwright 等の重量ライブラリ導入を前提にした試算だが、automation-maximalist の P1-3 提案は `tools/check_cjk_markdown.py` と同種の **数十行の grep スクリプト**（既存の自作ツールパターンに合致）であり、D-6 が禁じる「追加ライブラリ」には該当しない。yagni-guard の CI 時間試算（+150-300秒・flaky 率上昇）も P1-1/P1-2/P1-3 の実コスト（既存テストへの数行追加 + ブラウザ非起動の grep 1本）とは桁が違う。「テスト追加 = 重い」という一般化が、今回の軽量提案には当てはまらない。
- **結論**: yagni-guard の「実機体感は自動化できない」は维持されるべき一次原則だが、「ゆえに一切の安価な回帰プロキシも追加しない」は論理の飛躍。**安価で・誠実にスコープを開示した**（＝実機の代替を僭称しない）プロキシは追加すべきで、高価・虚偽の安心感を生む代替（visualViewport 等）だけを却下するのが正しい線引き。

### 更新した自分の立場（round1 からの差分）

1. `toBeFocused()`（P1-1）・build artifact grep（P1-3）は追加を支持に転じる（round1 では「候補タップで確定+ラベルON」を状態ロジックとして完全カバー済みと譲歩したのみで、フォーカス保持の回帰ガード追加は言及していなかった）。
2. 手動チェックリストの「重複なし」要件は、サーバー側 `request_ids`/`issue_log` 冪等性キーの発見により **撤回**。実機確認は「自動再送が発火するか」のみに絞る。
3. それ以外（WebAPK コールドスタート実測・実指タップ精度・実機フォント視認性・IME パネル表示継続そのもの）は round1 の主張を維持する。
