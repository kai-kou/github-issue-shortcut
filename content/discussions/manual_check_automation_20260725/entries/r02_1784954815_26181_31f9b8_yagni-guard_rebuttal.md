## 🔄 Round 2: yagni-guard の rebuttals 及び concession

### automation-maximalist の 4 提案に対する裁定

  - オフラインキューの再入保護（flushingRef ガード）の回帰検知にもなる

**✅ P1-3: `tools/check_sw_background_sync.py` で dist/sw.js を grep（"issue-post-queue" + "POST"）**

  - **ただし**「生成物の検査は build 直後であり、実装段階では検知できない」という後出し性に注意。新規 Bug 導入前でなく事後検知（差分コストなし・リスク相応）

### real-device-realist の「残余手動チェックリスト」の持続性評価

提案されたリスト（5 項目）に対する運用コスト評価:

| 項目 | コスト | 持続可能性 |
|------|--------|-----------|
| キーボード維持・レイアウト（interactive-widget） | 初回 5 分 + PR 時 2 分/回（IssueForm/index.html 変更時のみ） | ✅ 保守可能（変更が低頻度） |
| WebAPK コールドスタート 5 秒実測 | 初回 10 分 + リリースゲート時 10 分 | ✅ 妥当（6 時間毎の smoke.yml 頻度よりは少ない） |
| 機内→復帰で Background Sync 再送・重複なし | 初回 5 分 + PR 時 2 分/回（Service Worker 設定変更時のみ） | ✅ 保守可能 |
| 実指タップ精度（8px 間隔・D-6 準拠） | 初回 10 分 + UI 大幅改修時のみ | ✅ 低頻度で可 |
| 屋外光下での視認性 | 初回 5 分 + 配色変更時のみ | ✅ 低頻度で可 |

**評価**: real-device-realist が「過剰拡張を避ける」と明記した自己批判を含め、リスト項目は **状態的/DOM 的な部分を既に自動化した上での残余** に限定されており、質・量ともに妥当。手動必須化が広がりすぎて「毎 PR で必須」になる悪循環はない（トリガー型：PR スコープ限定 + リリースゲート限定）。

### 最終判定: E2E スイート追加の優先度

**P1-1, P1-2, P1-3 は**:
- 実装コスト: 最小
- CI 時間増加: ゼロ（既存 spec 内の assert/endpoint 追加）
- ライブラリ追加: ゼロ（D-6 遵守）
- 検知価値: 妥当（意図的コード・設定の回帰ガード）

- 参考値ガード（本実測ではない限界を明記）
- アプリ処理の劣化検知は可能

→ **4 提案全て採用・実装**。ただし automation-maximalist の docstring が「これら 4 点のみが正当な自動化」であることを明示する言葉を確認してから着手すること（曖昧だと「次は○○も追加」の蛇足議論に戻る）。

### 結論

1. **既存 E2E**: 機能的には 1-6 を完全カバー。追加で P1-1/P1-2 により信頼性向上
