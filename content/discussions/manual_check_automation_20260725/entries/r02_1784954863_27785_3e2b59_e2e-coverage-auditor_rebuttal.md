## e2e-coverage-auditor: Round 2 rebuttal/concession

### 1. automation-maximalist の追加提案 — 重複判定

- **P1-1（`toBeFocused()` を smart-input.spec.ts:87 直後に追加）**: **完全に一致・重複ではなく私の round1 ②-1 と同一結論**。新規ファイル・新規依存ゼロで唯一の真の未カバー（項目4のキーボード維持サブ項目）を埋める。これは支持する。
- **P2（kpi.spec.ts の同一テストに 5000ms の別 assert を追加）**: **これは重複と判定し却下すべき**。既存 `:128` の `expect(m.totalMs).toBeLessThan(10_000)` と、提案する 5000ms assert は **同一メトリクス（`totalMs`＝同一コードパスの起動→起票完了時間）に対する二重の閾値** であり、新しい失敗モードを検出しない（10s も 5s も同じ `totalMs` が超えたら失敗するだけで、5s 版が先に落ちるなら 10s 版は情報として無意味になる）。yagni-guard の「CI variance で環境依存の flaky が増える」という懸念（round1 ⑤）とも整合し、ここは yagni-guard 側を支持する。ただし理由は「YAGNI 全体論」ではなく「同一メトリクスへの重複 assert で新規カバレッジがゼロ」というカバレッジ監査固有の論点として明確化しておく。
- **P1-2（mock-github.mjs へ issue 作成回数カウンタ追加・重複なし直接検証）**: これは元の7項目チェックリスト（自分の round1 監査対象）の範囲外（lead メモが追加した8項目目「オフラインキュー再送で重複しない」に対応）。ただし lead メモ `:31` が「重複なしの検証は未実装（カウンタなし）」と明記しており、これは smart-input.spec.ts 系のどのテストとも重複しない **構造的に新規のカバレッジ**（現状「キューが消えた」という間接証拠しかなく「作成回数が1件」という直接証拠が存在しない）。yagni-guard が総括⑥で「大部分の自動化提案を却下」と一括りにしているが、これを却下対象に含めるなら誤り — 重複ではなく空白を埋める提案であり、コストも mock サーバーへのカウンタ1個+assert1行と最小。
- **P1-3（SW config regression grep）**: 同じく元の7項目チェックリストの範囲外、かつ E2E ではなくビルド成果物の静的検査なので「E2E との重複」は原理的に発生しない。yagni-guard が D-6 の根拠に挙げた `allure-playwright`/`checkly` 等の npm 依存とは性質が異なる（`tools/check_cjk_markdown.py` と同型の内製 grep スクリプトであり、追加 npm 依存ではない）。D-6 論法をここに適用するのは対象のミスマッチ。

### 2. real-device-realist の「エミュレーション不可能」主張 — 既存 E2E が実は等価カバーしている項目はないか

- 項目1・2・3・5・6の「完全に譲る」判定は自分の round1 表と完全一致。異論なし。
- 項目4「候補タップでキーボードが閉じない」について: real-device-realist は「DOM フォーカス保持と OS の IME パネル維持は別レイヤー」で「原理的に検証不能」と述べるが、これは **前提として実装（`IssueForm.tsx:209` の `onMouseDown preventDefault`）自体が「blur を起こさない」ことだけを保証する設計** である点を見落としている。real-device-realist 自身のコメント引用（「タップで入力欄からフォーカスが外れるとソフトキーボードが閉じてしまうため」）が示す通り、**blur → キーボードが閉じるは実機で確定した因果関係** であり、その逆（blur が起きない → キーボードは閉じない）は必要条件として真になる。つまり `toBeFocused()` は「キーボードが閉じない」ことの **十分条件までは証明できないが、この実装が壊れて blur が発生してしまう回帰（＝確実にキーボードが閉じる不具合）は 100% 検出できる**。「検証不能」と言い切るのは過剰で、実際には「必要条件の回帰ガードとしては完全に等価」というのが正確な評価。P1-1 を推す automation-maximalist・自分の判定とも整合する。
- 項目 (B)「`interactive-widget=resizes-content` と visualViewport」、(D)「SW Background Sync のタブを閉じた状態からの再送」、(E)「実指タップ精度・実機フォント視認性」は、いずれも **元の7項目チェックリストに含まれていない新規論点**（自分の round1 監査対象外）。real-device-realist が「手動に残す」と結論した粒度自体に異論はないが、これらを最終決定に含めるかはスコープ確認が必要 — lead/オーケストレーターが7項目チェックリストの範囲を拡張する合意をしたのかを明示してから採用すべきで、既存カバレッジ監査の立場からは「新規スコープの追加」として扱う（否定はしないが、7項目の枠外だと明記する）。

### 3. yagni-guard の却下リストに、カバレッジ上は本当に必要な項目が混ざっていないか

**混ざっている。** yagni-guard ④「YAGNI 適用」は「完了済み Issue #145/#16/#15 の確認手順を再現する E2E テストの追加」を却下し、キーボード関連の回帰ガードは「次にキーボード起動ロジックが変わった時まで」保留するとしているが、これは **P1-1（`toBeFocused()` 1行追加）を誤分類している**。P1-1 は「過去の手動確認の再現」ではなく、「既に本番実装済み・既にテストされている既存テスト（smart-input.spec.ts:49-102）の中に、実装済みロジック（`IssueForm.tsx:209` の `preventDefault`）を保護するアサートが1つだけ欠落している」というだけの話であり、新規テスト・新規ファイル・新規実行時間コストはゼロ（既存テストの実行回数・setup は変わらない）。yagni-guard の「却下」の論拠（CI 時間増加・flaky 率上昇・D-6 のライブラリ追加リスク）はこの1行には一切当てはまらない。yagni-guard の一括却下はカバレッジ監査の観点からは過剰包摂であり、P1-1 だけは却下対象から除外すべき。

一方、yagni-guard の P2（5s 閾値強化）への懸念、および新規スペック・新規ツール全般への慎重姿勢は、上記①②の分析とも整合しており、そこは支持する。

### 結論（自分の立場）

- 認めるべき最小差分: **P1-1 のみ**（既存テストへの1行追加。カバレッジ上の空白を唯一埋める）。
- 追加を検討してよい（元チェックリスト範囲外だが空白確認済み）: P1-2（mock issue 数カウンタ）。
- 却下すべき: P2（同一メトリクスへの重複 assert）。
- スコープ確認が必要（7項目の枠外・否定はしないが拡張の合意が要る）: real-device-realist (B)(D)(E)、P1-3。
