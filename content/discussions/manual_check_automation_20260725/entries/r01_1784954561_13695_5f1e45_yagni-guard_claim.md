## 🔒 YAGNI-Guard レビュー: 実機手動確認チェックリスト自動化の適切性判定

### 申し立て: 大部分の自動化提案を却下。最小限の回帰ガードのみ追加を認める

---

## ① 既カバー範囲 vs. 本当に未カバーの切り分け結果

**結論: 機能テストは既に十分カバーされている。自動化は大部分が重複。**

現状:
- `e2e/smart-input.spec.ts`: 7 テスト、277 行
  - @label トークン認識・送信時反映・除去 ✅
  - @label オートコンプリート提示・タップ確定 ✅
  - チップタップによる解除（トークン+ラベル連動） ✅
  - 大文字小文字混在での重複排除 ✅
  - LabelPicker チェック解除でトークンも除去 ✅
  - #repo フィルタリング・タイトル引き継ぎ ✅
  - #repo チップ解除で復元 ✅

これらはすべてモック GitHub・Pixel 7 エミュレーション上で完結している。

**提案で「手動確認が必要」とされるチェックリスト項目**（Issue #145/#16/#15 から推測）:
- 実機タップ精度（指が細い/太い、爪か指の腹か）
- 実機ソフトキーボード挙動（起動遅延、IME 設定による差異）
- WebAPK standalone コールドスタート（Service Worker キャッシュ復帰の体感）
- 実機フォント視認性（ディスプレイの pixel density・明るさ）

**判定**: エミュレーションで測れる機能テスト（「トークン認識が動く」「候補が表示される」）は既に自動化済み。
**エミュレーションでは測れない項目**（「タップが指の微妙な位置ズレで反応するか」「キーボードが実際に何ms遅延するか」）は、どうあがいてもスクリプト自動化では代替不可。

→ 仮に自動化スクリプトを書いても、「Pixel 7 エミュレーション上でテストが通った」≠「実機で体感的に OK」。

## ② エミュレーション vs. 実機の線引き（定量的）

**既定値を追認する**:
- `playwright.config.ts`: `fullyParallel: false` (並列不可) + `workers: 1` (単一ワーカー)
- CI で `retries: 2`（非同期 UI 更新が遅延して flaky になることを認識）
- 現在 ~40 個の E2E テスト（総行数を確認: 17 spec × 平均 150-300 行）

**エミュレーション E2E の信頼性上限**:
```
現在: 40 テスト × 30 秒 timeout = 最大 1,200 秒（20 分）
     実際: CI retries=2 + flaky 問題で体感 40-50 分

提案で 5-10 個の追加テスト: +150-300 秒の増加
     → 実機体感テストを「代替」できるわけではなく、単にスイート時間が増え、
       environment variance（CI マシン性能・ネットワーク・スケジュール）による flaky がさらに確率的に上昇
```

**結論**: テスト追加は CI 実行時間と flaky 率の両方を悪化させる一方、
「実機で本当に動くか」への答えは 0 本増える。

## ③ D-6「追加ライブラリゼロ原則」への違反リスク

**提案のいずれかの部分で、以下が必要になるはず**:
- Checklist HTML 生成ツール（JSON spec → 実行可能な .md / Issue コメント）
- 実行結果記録ツール（Pass/Fail × チェック項目 をファイル保存・Issue コメント化）
- CI integration（smoke.yml vs ci.yml の判定・条件付き実行）

**D-6 違反判定**:
- ライブラリ: allure-playwright（Playwright 統合レポート）、checkly（継続的 E2E）等が候補だが、すべて `package.json` に追加が必須
  → バンドル予算 80KB / 35KB の枠外（devDependencies なので直接効果なし、でも総 node_modules 肥大化）
- カスタムツール: Python/Node でチェックリスト生成スクリプトを書いても、「1 回の機能追加検証のためだけのツール」になり、スケーラビリティゼロ

## ④ YAGNI 適用: 「1 回だけ実行する自動化」の却下

**却下対象**:
> 「既にクローズ済み Issue #145/#16/#15 の確認手順を再現する E2E テストを追加する」

根拠:
1. 機能はもう実装済み（commit 3e70400 で既にマージ済み）
2. 「その時点での手動確認」はもう終わった（履歴記録のための再現テスト）
3. 今後の回帰を防ぐためなら、E2E ではなく「機能が変わったら自動的に実行される回帰テスト」であるべき

実例: D-8「楽観的 UI は救済とセット」という原則で error handling の追加実装まで待ってから
      スイート実行。それ以前の PoC テストは必要なし → 同じロジック。

**許可対象（最小化）**:
> 「もし今後キーボード起動ロジックや #repo フィルタ条件が変わったら、
>  smart-input.spec.ts の既存テストで自動的に回帰を検知できるスコープ内での保守」

このスコープなら：
- 既存 7 テストで十分（新規追加なし）
- E2E 実行時間増加なし
- D-6 違反なし

## ⑤ 5 秒 KPI の自動化形態（定量的懸念）

提案で「5 秒 KPI を assert に強める」案に対する懸念:

```
kpi.spec.ts の現在の立場（コメント抜粋）:
  ✅「アプリ処理が遅くなっていないか」の監視（回帰ガード）
  ❌「WebAPK/standalone のコールドスタート・実機ソフトキーボード遅延・
      CPU throttling といった実機体感は含まない」
  ❌ 本 spec の合否は NFR-2 の実機 10 秒基準の代替ではない

threshold assert 強化の問題:
- 環境 variance（CI マシン性能・GC タイミング）により
  「本当は実機で 4.5 秒」でも「CI エミュレーション上で 5.2 秒」の可能性
- 「E2E が 5.1 秒だから本番は OK」という誤認を招く
- 実際の 5 秒基準は「実機での体感計測」が本来のプロフ値であるべき
```

**推奨**:
- 5 秒基準は「参考値」のまま（assert 強化しない）
- 本当の KPI（NFR-2）は定期的な実機計測で監視（別プロセス）
- E2E は「回帰（= 前回より遅くなった）」検知に限定

→ 自動化の過度な信頼は危険。定期実機測定の方が安い。

## ⑥ 総括と却下理由

**却下**:
1. **既存 E2E でカバー済み**: smart-input.spec.ts で機能は網羅
2. **実機テストは自動化不可**: エミュレーションで softkey 遅延・WebAPK cold start は計測できない
3. **スイート時間悪化**: テスト追加→ CI 時間 +40-50 分、flaky 率上昇、得られる新情報ゼロ
4. **D-6 違反**: 新規ツール/ライブラリが必須で、バンドル・運用負荷増
5. **YAGNI**: 完了済み Issue の「かつての手動確認」を再現するテストは 1 回限りコスト

**認可（最小化）**:
- smart-input.spec.ts の既存 7 テストの保守（機能変更時の回帰ガード）
- kpi.spec.ts の参考値維持（threshold 強化しない）
- 実機 KPI 計測は別プロセスで定期実施（E2E に統合しない）

**実行予定タイミング**: 次の大きなキーボード/フロー改修時に、
「その時点での機能変更に対してのみ」既存テストで回帰確認。
チェックリスト自動化ツール化は不要。
