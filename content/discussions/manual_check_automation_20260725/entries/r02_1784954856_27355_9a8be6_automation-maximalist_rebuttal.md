## Round 2: rebuttal + 一部 concession

### 対 e2e-coverage-auditor
「対 automation-maximalist への先回り反論」（項目1/2/3/5/6への新規テスト追加を却下）は **私が round1 で提案していない主張への反論**（藁人形）。round1 の私の提案（P1-1〜P1-3・P2）は既存テストへの1行追加または offline-queue.spec.ts への1本追加のみで、①〜⑥の✅項目に新規スペックを足す提案は一度もしていない。したがって①の判定・③の重複回避ロジックには全面同意する（争点なし）。

一方、あなたの対応表は「チェックリスト1〜7」のみを対象にしており、私が round1 で追加提案した **オフライン重複なし（mock-github 作成回数カウンタ）** と **SW Background Sync 設定のビルド成果物 regression ガード** は表の対象外（lead メモの「オフラインキュー再送で重複しないこと」行はあなたの表に含まれていない）。ここは未反論のまま残っている点を指摘する。

### 対 yagni-guard（反論主体・一部 concession）

**実行時間見積もりへの反論**: あなたの「5-10 個の追加テストで+150-300秒、体感40-50分」という試算は、私が提案していない規模を前提にした藁人形。私の実提案は次の4点のみ:
- P1-1: 既存テスト内に `toBeFocused()` を1行追加（新規テストではない・追加実行時間 ≈0秒）
- P1-2: `offline-queue.spec.ts` に **新規テスト1本のみ** 追加（online 二重発火の再入ガード回帰）。中身は既存の "オフライン時にキュー表示され…" テストとほぼ同一構造で、`RETRY_INTERVAL_MS=2000ms` のリトライ待ちが1回発生する程度 → 追加時間は **約2〜5秒**
- P1-3: `npm run build` 後に `dist/sw.js` を grep するだけの Python スクリプト。ブラウザ起動なし・**追加時間1秒未満**。CI の `test` ジョブは既に `npm run build` を2回走らせている（#137 回帰ガード用）ので、そこに乗せるだけで新規ジョブも不要
- P2: 既存 `kpi.spec.ts` の同一テスト内に assert を1行追加（新規テストではない・追加実行時間≈0秒）

**合計追加コスト: 新規テスト1本・約2〜5秒。あなたの見積もり（40-50分）とは2桁違う**。「実測して反論せよ」という lead の指示どおり、数値で応答した。

**D-6（新規ライブラリ禁止）への反論**: `allure-playwright`/`checkly` は私は一度も提案していない。P1-3 は Python 標準ライブラリのみ（既存の `check_cjk_markdown.py` と同型）、P1-2 は既存 `mock-github.mjs`（Node 標準 `http`）にカウンタ変数を1個足すだけ。**新規 devDependency はゼロ**。ここも藁人形。

**5秒閾値の環境分散リスクへの concession（部分譲歩）**: これは正当な指摘として受け入れる。CI マシン性能・GC タイミングのブレで「実機なら4.5秒でも CI で5.2秒」という偽陽性は確かに起こりうる。round1 の P2 提案（5000ms のハード assert 追加）は **撤回し、非ブロッキングな形に格下げする**: 既存の `collected`（`test-results/kpi-metrics.json` に既に全量出力済み・kpi.spec.ts:89-95）に対し、5秒超過時は `console.warn` するだけに留め、テスト失敗（CI 赤）にはしない。10秒のハード assert（既存）はそのまま維持。これで「回帰の早期発見」という目的は保ちつつ、あなたの懸念（false failure による flaky 化・過信）を解消する。
