## ② 統合提案: 「使い方セクション」系の重複を 1 箇所に集約する

newcomer #1 と自分の #2（PWA インストール手順）・#3（Organization 承認待ち）・#4（ログイン 2 ステップ）は、実質すべて同じ欠落「README に時系列の使い方ステップが無い」の別側面。**4 本の個別パッチとして README のあちこちに一言ずつ足すと、かえって断片的な注記だらけになり読みにくくなる**（①で懸念した肥大化そのもの）。

統合案: 「なぜ作ったか」の前後（newcomer 提案の位置に同意）に、**4 行の番号付きステップだけ**を追加する。

```
1. GitHub でログイン（Issues の読み書きのみ許可）
2. 起票したいリポジトリへ GitHub App をインストール（Organization は管理者承認待ちになる場合あり）
3. ブラウザのメニューから「ホーム画面に追加」
4. ホーム画面のアイコンをタップして起票
```

これで newcomer #1・自分の #2/#3/#4 の 4 件が **1 箇所・4 行**で解消する（newcomer 提案の既存ログインスクショの再利用も活きる）。個別に 4 箇所へ注記を散らすより軽い。

## rebuttal: oss-contributor の重大度付けは project-mission.md の優先順位と矛盾する

`docs/project-mission.md`「優先順位付け（迷ったとき）」は明記している。

```
1. 起票の速さ・確実さ（コア体験）
2. セットアップの容易さ
3. 起票の表現力
4. ドキュメント・運用改善
```

CONTRIBUTING.md・ISSUE_TEMPLATE・PR_TEMPLATE・CODE_OF_CONDUCT は明確に「4. ドキュメント・運用改善」に属する。個人開発者 1 人 + AI エージェント運用（README「AI エージェントによる自律開発運用」節）という現状の開発体制を踏まえると、外部貢献者の PR が来る前提の重装備（行動規範・PR テンプレート）を今 P1 で用意する優先度は、実利用者が初回起票に到達できない欠落（自分の #1〜#4）より低いはずである。**「一般公開前提」＝ユーザー公開であって、コード貢献者受け入れの公約ではない**（README・要件書とも「誰でも GitHub ログインで利用できる」であり「誰でもコード貢献できる」とは書かれていない）。oss-contributor の Critical 判定は「外部貢献者の参入を妨げる」を基準にしており、これは今回の議題（README・公開ドキュメントが利用者の初回体験・信頼判断をどう助けるか）の主軸である「利用者が使い始められるか」とは異なる評価軸である。package.json の license 欠落のみは実害（npm 公開時の実務問題）が具体的なので P1 で妥当と考える。CONTRIBUTING.md 等は P3（低優先）へ格下げを提案する。
