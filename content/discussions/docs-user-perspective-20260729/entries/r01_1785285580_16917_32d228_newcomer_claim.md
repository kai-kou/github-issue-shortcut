## newcomer レンズ: 初訪問者としての README / 関連ドキュメント検証（Round 1）

前提: 実際に対象ファイルを通読した上での指摘。「書かれていない」と断定する箇所は該当行を明示する。

### 1. 【高】「使い方（インストール手順）」のセクションが存在しない
- **該当**: README.md 全体（特に L.30-51「できること」〜「目指している速さ」の間）
- **問題**: 「ホーム画面をタップして数秒で…」（L.7）と冒頭で謳っているのに、「👉 アプリを開く」（L.13）をタップした後に何が起きるか（GitHub ログイン → OAuth 同意 → ホーム画面に追加）を順を追って説明する箇所が無い。screenshots の 3 枚（起票フォーム/スマート入力/ログイン）はあるが、それを「① ログイン → ② ホーム画面に追加 → ③ タップで起票」という時系列のステップとして並べていない。
- **初訪問者への影響**: リンクを押した後、GitHub の OAuth 同意画面に着地して初見で戸惑う。「ホーム画面に追加」の操作（Android Chrome の追加方法）も自明ではなく、ここで離脱しやすい。
- **推奨修正**: 「なぜ作ったか」の前後に 3 ステップの「使い方」セクションを追加し、既存のログイン画面スクショを再利用してステップ 1 に充てる。

### 2. 【中〜高】「ショートカット」という語が定義前に使われる
- **該当**: README.md L.9「ショートカットがリポジトリとラベルを覚えているので、タップした時点で入力欄にカーソルが立っています。」
- **問題**: この時点で「ショートカット」が (a) Android ホーム画面のアイコン、(b) PWA の manifest shortcuts 機能、(c) プロダクト名自体（"Issue Shortcut"）のどれを指すか読者には判別できない。具体的な仕組み（URL パラメータでの初期選択、アイコン長押しメニュー）は L.33-34 まで出てこない。
- **初訪問者への影響**: 冒頭 30 秒で「これは何か」を掴む妨げになる。プロダクト名と機能名が同じ単語のため特に混同しやすい。
- **推奨修正**: 初出時に括弧書きで一言添える（例:「ショートカット（ホーム画面のアイコン）」）か、L.9 を「できること」節の後に回す。

### 3. 【中】CTA（アプリを開く）の前に、何を許可させられるかの説明がない
- **該当**: README.md L.13「👉 アプリを開く」は「要求する権限は Issues（Read and write）のみ」（L.32）より **前** に配置されている
- **問題**: L.11 で「サーバーはデータを保存しない」という安心材料は先出しされているが、OAuth で具体的に何の権限を求められるか（コードには触れない、Issues のみ）は CTA の後、スクリーンショット・「なぜ作ったか」を挟んだ 20 行以上先。初訪問者は CTA を押す前にこの安心材料を得られない。
- **初訪問者への影響**: 見知らぬ GitHub App への権限付与に慎重な人ほど、CTA 直前に許可範囲の一言が無いと足踏みする。
- **推奨修正**: CTA の直下か同じブロックに「要求する権限は Issues の読み書きのみ・コードには触れません」を 1 行追加。

### 4. 【中】英語版 README が存在せず、非日本語話者は完全に置いていかれる
- **該当**: README.md 全体（英語の記述なし）。アプリ自体は L.40「日本語 / English の 2 言語対応」
- **問題**: アプリ本体は英語 UI を持つのに、GitHub 上の入口である README は完全に日本語のみ。英語話者が GitHub の検索・トレンド経由で来訪した場合、「これは何か」を判断する材料が一切ない。
- **初訪問者への影響**: 個人 OSS の規模を考えれば全訳は過剰要求だが、最低限「これは何のツールか」を 2〜3 行で伝える英語サマリーの欠如は、潜在ユーザーの取りこぼしに直結する。
- **推奨修正**: README 冒頭に 2〜3 行の英語 tagline を追加する程度で十分（全訳までは不要）。

### 5. 【低〜中】SECURITY.md がトークン設計の詳細ドキュメントにリンクしていない
- **該当**: SECURITY.md L.14「対象範囲」に「認証フロー（GitHub OAuth・トークンの取り扱い）」とあるが、`docs/design/stateless-architecture.md`（トークンの暗号化 Cookie 設計を実際に説明している文書）への参照が無い
- **問題**: セキュリティを気にして SECURITY.md を読みに来た初訪問者が、「具体的にどう扱っているか」を知る導線を失う（README L.65 には design doc へのリンクがあるが、SECURITY.md 単体では辿れない）。
- **推奨修正**: SECURITY.md の「対象範囲」に stateless-architecture.md への 1 行リンクを追加。

### 6. 【低】スクリーンショット表の並び順が体験の時系列と逆
- **該当**: README.md L.15-17 の表: 起票フォーム → スマート入力 → ログイン
- **問題**: 実際の初回体験順は ログイン → 起票フォーム → スマート入力 のはず。現状の並びだと「まず何をするか」が視覚的に伝わりにくい。
- **推奨修正**: 列順を ログイン → 起票フォーム → スマート入力 に入れ替える。

### 7. 【低】「サーバーはデータを保存しません」の主張が唐突（文脈なしで先出し）
- **該当**: README.md L.11
- **問題**: この時点ではまだ「PAT 管理不要」「GitHub ログインのみ」程度の情報しかなく、なぜ「データを保存しない」が重要な安心材料なのか（＝トークンを預かるリスクの回避）の文脈が無いまま太字で断定される。
- **初訪問者への影響**: 大きな影響ではないが、なぜこの一文がここにあるのか一瞬迷う。項番3の「権限説明を CTA 近くに移す」修正と合わせて、L.11 の直後に一言（例:「あなたの GitHub トークンを他社サーバーに預けない設計です」等）を足すと繋がりが良くなる。
- **推奨修正**: 項番3とセットで、CTA 周辺の文脈を再構成する際に統合して直す。

### 8. 【低】docs/requirements/README.md は未定義の略語が多く、README からの導線先として初訪問者には重い
- **該当**: docs/requirements/README.md 全体（`MVP`・`OQ-7`・`NFR-13` 等）。README.md L.91 の「ドキュメント」節からリンクされている
- **問題**: README.md 本体からの「興味があれば」導線として提示されているため致命的ではないが、リンク先がいきなり要件定義の専門用語（Issue トレーサビリティ ID 等）で構成されており、アプリを試したいだけの初訪問者が迷い込むと離脱しやすい。
- **推奨修正**: 対応不要（優先度低）。あえて直すなら README.md 側のリンク文言に「開発者向け」等の一言を添え、期待値を調整する程度で十分。
