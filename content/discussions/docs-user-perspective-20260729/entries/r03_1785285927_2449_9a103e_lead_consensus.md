## lead: 合意点・対立点の整理（Round 3）

議論を経て、4 レンズの 29 件の指摘は **「利用者の初回体験・信頼判断」を止める真の欠落 8 件** と、**規模不相応・好み・重複として除外された項目** に分離した。lead 側で全 critical をリポジトリの実ファイルで裏取り済み（伝聞のまま採用していない）。

### 合意 1: 最上位は「README の記述と実装の直接矛盾」（2 件）

議論で唯一「実装が自ら README を否定している」ことを一次証拠で示せた項目群。誤情報は不足より重い。

- **ホーム画面ショートカット**: README「`/new?repo=...` …ホーム画面にいくつでも並べられます」に対し、`src/i18n/translations.ts` L302-303 の `placementGuideNote` が「この URL を単体でホーム画面のアイコンにしても、初期選択（プリセット）は反映されません（Android の仕様）」と警告している。target-user が検出し、oss-contributor が grep で裏取り、newcomer が自身の弱い指摘（用語の曖昧さ）を撤回してこちらを支持。lead でも該当行を確認済み。
- **オフライン再送**: README「二重起票はしません」に対し、実装は `queueExpired`「24 時間以上送信できなかったため、自動再送を停止しました。GitHub 側に作成済みでないか確認してから、再送または破棄してください」と手動対応を求め、要件書 §7.1 は重複起票の可能性を P3 で受容している。lead でも文言を確認済み。

### 合意 2: 信頼判断の導線欠落（2 レンズが独立に同一結論）

trust-privacy #1 と target-user #6 が別の切り口から同じ穴に到達した。README に `privacy` / `terms` の語が **0 件**（lead が grep で確認）である一方、アプリには `/privacy` `/terms` が実装済み（`src/App.tsx` L229・L251-252）。書き込み権限を渡す前に規約を読む導線が、入口である README から断たれている。

### 合意 3: README が名指しする裏取り文書自体が古い

`docs/research/2026-07-28-data-retention-inventory.md` §9 は、アカウント削除の範囲を「⚠️ 不一致」と結論したまま。しかし実装は `src/auth/useAuthState.ts` L69-82 の `clearAllLocalUserData()` が「未送信の下書き・オフラインキューまで含めて全消去する（#181）」と明記し、`clearDraft()` / `clearOfflineQueue()` / `clearSentRequestIds()` を呼んでいる（lead が実コードで確認）。README がこの文書を「全数棚卸し」として信頼の根拠に挙げているため、裏取りに来た慎重な読み手ほど誤った不信を持つ。**欠落より有害な種類の古さ**。

### 合意 4: 「使い方ステップ」系の 4 指摘は 1 箇所に統合する（README 肥大化の回避）

newcomer #1（使い方セクション不在）・target-user #2（PWA インストール手順）・#3（Organization 承認待ち）・#4（ログインは実は OAuth 認可 + App インストールの 2 段）は、すべて同じ欠落の別側面。target-user の統合案（番号付き 4 ステップを 1 箇所に置く）を採用する。4 箇所へ注記を散らすと、起票速度を売りにするプロダクトの入口が断片的な但し書きだらけになる。

### 対立点と決着 1: 「安心文言を CTA 直前へ移す」提案の条件付き採用

newcomer #3 は権限説明を CTA 直前へ移すことを提案。trust-privacy が反論した — 「Issues（Read and write）のみ」は要件書 §4.2-2 の実態（Issues: write + 自動付与の Metadata: read）より粗く、検証手段も示されていない。**不正確な断定を、読者が最も判断力を働かせる場所に押し出すことになる**。

**決着**: 位置の移動は採用するが、単独では採らない。移動と同時に、GitHub のインストール画面で実際の要求権限を確認できる旨を併記する（trust-privacy #6 と target-user #7 の統合形）。目立たせる場所ほど正確性の要求水準を上げる、という反論を正とする。

### 対立点と決着 2: 貢献者導線ファイルの重大度（oss-contributor vs target-user + newcomer）

oss-contributor は CONTRIBUTING.md / ISSUE_TEMPLATE / PULL_REQUEST_TEMPLATE / CODE_OF_CONDUCT の欠落を Critical・P1「即時実装必須」と判定。target-user と newcomer が独立に反論した:

- `docs/project-mission.md` の優先順位で「ドキュメント・運用改善」は 4 位（最下位）
- 「一般公開前提」は **利用者への公開** であって、コード貢献者受け入れの公約ではない（README・要件書とも「誰でも GitHub ログインで利用できる」としか書いていない）
- 今回の議題の主軸「利用者が使い始められるか」とは評価軸が異なる

**決着**: Critical 判定は退ける（**P3 へ格下げ**）。ただし欠落そのものは事実であり、本 PR のスコープ外として別 Issue にする。例外は `package.json` の `license` 欠落（lead が確認済み）— 1 行で直り、ライセンス表記の一貫性は公開 OSS の実務事項なので本 PR に含める。
