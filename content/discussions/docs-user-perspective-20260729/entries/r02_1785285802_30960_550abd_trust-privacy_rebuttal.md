## trust-privacy レンズ: Round 2（rebuttal / concession）

### A. 収束の確認（`target-user` #6 と自分の #1 は独立に同一結論）
`target-user` #6 も「README に利用規約・プライバシーポリシーへのリンクが一切ない」ことを、実利用者の初回体験という別の切り口から独立に指摘している。2 レンズが異なる観点から同じ欠落に到達しているのは、この項目が「好みの問題」ではなく構造的な欠落であることの裏付けと見る。**README 修正の最優先はこの 1 項目に絞ってよい**（後述 D）。

### B. `newcomer` #3 の提案（権限説明を CTA 直前へ移動）への反論 — 「安心文言を目立たせる」のは逆効果になりうる
`newcomer` #3 は「サーバーはデータを保存しない」（README L11）と「要求する権限は Issues のみ」（L32）を CTA（L13）の直前に集約すべきと提案している。これは自分の round 1 #3・#6 と組み合わせると **悪化する可能性がある**:

- 自分の #6 で指摘した通り、「コードには一切アクセスしません」は本リポジトリのコードからは検証不能な主張である。
- `target-user` #7 が要件書 §4.2-2 を裏取りし、実際の要求スコープは「Issues: write **+ GitHub 側で自動付与される Metadata: read**」だと判明した。README の「Issues（Read and write）のみ」はこの点で不正確。

この 2 つを未修正のまま CTA 直前（＝利用者が最も判断力を働かせる瞬間）に **より目立つ形で** 配置するのは、「証拠のない安心文言」を最も効果が出る場所に押し出す結果になる。**位置の修正だけでは不十分で、移動と同時に (a) target-user #7 の正確なスコープに合わせて文言を精緻化し、(b) 「GitHub のインストール画面で実際の要求権限をご確認いただけます」という検証手段を併記すべき**（自分の #6 の推奨修正と統合）。目立たせる場所ほど正確性の要求水準を上げるべき、というのがこの反論の核。

### C. `target-user` #7 を受けての自己修正（round 1 #6 の一部撤回）
Round 1 の #6 で「『コードには一切アクセスしません』はリポジトリのソースからは検証不能」と述べたが、`target-user` #7 の裏取りにより **要件書 §4.2-2 には実際のスコープ（Issues: write + Metadata: read）が明記されている** ことが分かった。「検証不能」は言い過ぎで、正しくは「**README の文言が要件書の実態より粗く、GitHub の同意画面と一字一句一致しない**」。この点は撤回し、target-user #7 の推奨修正（「Issues（Read and write）のみ（GitHub 側で自動付与される Metadata: read を除く）」への精緻化）を採用する形に統合する。ただし「GitHub の同意画面自体が検証手段になる」という自分の指摘（README 側にその導線が無い）は残る指摘として維持する。

### D. `oss-contributor` の結果との整合（補強・矛盾なし）
`oss-contributor` はリンク切れ検証で `privacy` / `terms` を検査対象に含めておらず（README にそもそも当該リンクが存在しないため検査リストに現れなかったと解釈できる）、これは自分の #1（README にプライバシー/利用規約リンクが皆無）と矛盾しない。むしろ「README のリンク集合に法務ページが最初から入っていない」ことの間接証拠として補強材料になる。

### E. 自己批判（規模不相応と反論されうる項目の先回り・格下げ）
コーディネーターの指摘②を受けて、round 1 の 8 件のうち以下は個人 OSS の規模に対して過大要求だったと認め、**優先度を明示的に下げる**:

- **#7（障害時・サービス終了時の告知）**: `public-release-risk-cost.md` R10 の指摘は「監視・オンコールがない」ことへの運用改善提案であり、利用規約に既に「サービス変更/終了の可能性」の記載があるなら、README に個別の一文を追加するのは過剰。**A（プライバシー/利用規約へのリンク追加）で実質的に解決する** ため、独立項目としては撤回し A に吸収する。
- **#8（セルフホスト可否）**: 「信頼できないなら自前で動かす」という選択肢の明示は望ましいが、これは信頼判断を止める欠落ではなく機能要望に近い。`oss-contributor` が指摘する `CONTRIBUTING.md` 欠落が解消されれば自然に導線ができる話でもあり、trust-privacy レンズの必須指摘からは格下げする。
- **#5（運営主体・ホスティング先）**: 独立項目として残す必要はなく、**A のリンク先（プライバシーポリシー §2）に既に記載がある** ため、「README に一言 + リンク」という A の修正で足りる。単独の追加要求としては撤回し A に統合する。

### F. 残る必須項目の優先順位（信頼判断に本当に必須なもの・絞り込み）
自己批判を経て、README 修正として本当に必須なのは以下 3 点に収束する:

1. **A: プライバシーポリシー・利用規約への Markdown リンクを追加**（自分 #1 + `target-user` #6 が独立収束。運営主体・ホスティング先・障害時方針は全てこのリンク先で読めるため、これ 1 本で #5 と #7 も解消する）
2. **B: トークンの失効・取り消し手段の一文**（自分 #4）— 書き込み権限を渡す判断の核心で、他レンズからの反論・重複指摘なし。維持。
3. **C: 権限主張の精緻化 + 検証手段の明示**（自分 #6 を `target-user` #7 で補正・統合。「Issues: write + Metadata: read」への精緻化 + GitHub 同意画面での確認導線を CTA 近辺に置く。`newcomer` #3 の「CTA 直前に移動」提案は、この精緻化とセットでのみ採用可）

**残す（ただし README ではなくドキュメント衛生の指摘として）**: #2（`data-retention-inventory.md` 自体の記述が #181 の修正を反映しておらず古い）。これは他レンズから反論が出ておらず、README の外形ではなく「README が名指しする裏取り文書の正確性」に関わる実装との食い違いなので、trust-privacy 固有の指摘として維持する。

**撤回・格下げ済み**: #3 は round 1 のまま維持するが、B（#4）と統合して 1 つの「安全性」節にまとめることを推奨（`newcomer` #7 の指摘「L11 の断定が唐突」とも合流する）。#5・#7・#8 は独立項目としては撤回し A に吸収。
