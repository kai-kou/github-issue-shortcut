## ops-risk 反論（Round 2）

### ① measurement-design への応答: 「誰がいつ見るのか」「運用が続くか」で採点し直す

measurement-design の判定表（`whiteboard.md:118-130`）と代替比較表（`whiteboard.md:153-165`）は「何が測れるか」の精度では完全に同意する。ops-risk レンズとして付け加えたいのは、**その先の「誰が見るか」の軸で採点すると、GA4 と Workers Analytics Engine（WAE）の優劣が一部逆転する**という点だ。

- WAE は「アーキテクチャ整合性が高い」「低母数でも生データがそのまま読める」（`whiteboard.md:157-160`）が、**可視化は自前構築**（`whiteboard.md:162`「×。SQL API のみ。可視化は自前 or Grafana 等の追加構築」）。個人 1 人・オンコールなし運用（brief (m)）でこの「自前構築」を実際にやり切り、かつ**継続してメンテする**シナリオを想定すると、GA4 の「UI ダッシュボードが最初から完備」という利点は、measurement-design が言うほど軽視できない。可視化を自分で作らなければ、WAE は「クエリを叩けば見える」ではなく「クエリを叩く気力がある日だけ見える」に劣化する。
- しかし逆に言えば、**GA4 の UI ダッシュボードが「完備」であることは「見に行く習慣ができる」ことを保証しない**。measurement-design 自身が④で指摘する通り「自トラフィック除外のパラドックス」（`whiteboard.md:171`）と「母数 1 桁〜数十件/週での統計的意味」（`whiteboard.md:172`）により、**仮にダッシュボードを見に行っても、そこに映る数字は意思決定に使えるほど有意ではない**。見やすいダッシュボードに無意味な数字が並ぶ状態は、「見に行く習慣」を逆に殺す（1〜2 回覗いて「動いていないのと同じ」と判断すれば、それ以降誰も見なくなる。これは個人開発でよく起きる計装の末路）。
- **結論（譲歩を含む）**: measurement-design の「GA4 を採る積極的理由は見出せない」（`whiteboard.md:189`）に同意する。ただし理由は「WAE の方が技術的に優れているから」ではなく、**「どちらのツールも、今の 1 人トラフィックでは "見て意思決定する" というループが成立しないから」**。ops-risk の立場では、ツール選定（GA4 vs WAE）は本質的な論点ではなく、**「継続して見る運用が始まる条件が整うまでは、どちらを選んでも死蔵する」**という点を強調したい。measurement-design が推す `e2e/kpi.spec.ts` の継続（`whiteboard.md:174,189`）は、**"見る運用" を新規に立ち上げる必要が無い**（CI が自動で assert する）という一点で、GA4 にも WAE にも無い運用コストゼロの優位性を持つ。ops-risk レンズからもこれを支持する。

### ② frontend-perf への応答: SP 見積もりを使って #171 との優先順位を定量的に再主張する

frontend-perf の見積もり（`whiteboard.md:274`）: 「gtag.js フル対応は 3〜5SP、Measurement Protocol（Worker 側）は実装 2SP + テスト 1SP ≒ 3SP」。この数字を `project-mission.md` の SP 工程別標準値（`project-mission.md:48-54`）に当てはめる。

| 対応 | SP 見積もり | 対応する工程区分（`project-mission.md`） |
|---|---|---|
| Cloudflare 使用量アラート設定（#171・NFR-14 の MUST 未達解消） | `sp:1`（「設定・データ更新・1 行修正」＝ダッシュボードでの通知ポリシー設定のみ。実装コードなし） | 機械的変更 |
| GA4（Measurement Protocol・frontend-perf 推奨方式） | `sp:3`（frontend-perf 実測見積もり） | 標準タスク相当 |
| GA4（gtag.js フル対応） | `sp:3〜5` | 標準〜複数ファイル横断 |

つまり **#171 を閉じるコストは、GA4 導入コスト（最も安い MP 方式ですら）の 1/3 以下**。しかも #171 は NFR-14 という **MUST 未達**（`docs/requirements/00-requirements.md:191`）の解消であるのに対し、GA4 は FR-26 という **SHOULD**（`00-requirements.md:138`）の実装候補の一つに過ぎない。「重要度は MUST > SHOULD」「コストは #171 が GA4 の 1/3 以下」という **2 軸とも #171 が優先** という結論になり、これは Round 1（`whiteboard.md:57`）で定性的に主張した内容を、frontend-perf の実測 SP で定量的に裏付けたことになる。

さらに frontend-perf の可逆性評価（`whiteboard.md:281`「Measurement Protocol は Worker 側の関数を削除するだけ・0.5SP 未満」）を踏まえても、**「安く戻せるから今すぐ試す」という判断にはならない**。可逆性が高いことは「試すコストの低さ」ではなく「撤退コストの低さ」を意味するだけで、③で述べる法務対応コストは撤去しても消えない（一度 Google に送信されたデータの扱いは privacy-legal 領域で別途対応が要る）。

### ③ privacy-legal への応答: 法務対応コストを運用負荷として合算し、費用対効果を再計算する

privacy-legal の結論は「adopt-conditional」で、必須の 5 点セット（`whiteboard.md:299`: ①クエリ文字列混入遮断（実装）②プライバシーポリシー全面改訂 ③越境移転・第三者提供の開示 ④EU 訪問者向け同意ゲート ⑤Google DPA 締結）を課している。これを frontend-perf の実装 SP に **上乗せするコスト**として ops-risk の総コスト表に統合する。

| 項目 | 誰の見積もり | SP 換算（ops-risk 試算） |
|---|---|---|
| MP 実装 + テスト | frontend-perf | 3 SP |
| クエリ文字列除去（`page_location`/`page_path` サニタイズ + 許可リスト方式のイベント設計） | privacy-legal ④・measurement-design②の設計を合成（`whiteboard.md:136,332-334`） | 2 SP（frontend-perf の 3SP に一部重複するが、privacy-legal が要求する「許可リストで repo/title/body を一切送らない」実装は frontend-perf の見積もりに明示的には含まれておらず、追加分として計上） |
| プライバシーポリシー全面改訂（`src/i18n/translations.ts` 日英両方・新設セクション） | privacy-legal（`whiteboard.md:340-352`） | 2 SP（`project-mission.md:52`「複数ファイル横断の機能実装」相当。日英 2 言語 + 利用規約整合 + 要件定義書 3 ファイルへの反映） |
| **EU 同意ゲート（同意バナー UI + 同意前は計測しない分岐）の新規実装** | privacy-legal（`whiteboard.md:321`） | 2〜3 SP（**新規 UI コンポーネント**。ミッション判断基準「起票フローに 1 タップでも追加する機能は既定でオフ・後回し」`project-mission.md:24` には直接抵触しないが（起票フロー外の初回訪問時 UI）、それでも新規のユーザー向け UI を 1 つ追加する意思決定であり、YAGNI 原則`project-mission.md:27`との緊張がある） |
| Google DPA 締結・設定確認（管理画面手続き） | privacy-legal（`whiteboard.md:356`） | 1 SP（設定作業のみだが「非技術的な法務手続き」を個人開発者が正しく行う不確実性を Dynamic 補正で加算） |
| **継続監視**: Schrems III 係属中訴訟のウォッチ（`whiteboard.md:311,373`「revisit_triggers に含めるべき」） | privacy-legal | SP 換算不能・**恒久的な運用負荷**（ここが最大の懸念） |

**合計: 実装だけで 10〜11 SP相当**（`project-mission.md:58` の上限ルール通り「8 超は分割を検討」に該当する規模）。これは frontend-perf 単独の見積もり（3〜5SP）の **2〜3 倍**に膨らむ。加えて Schrems III のような **完了しない継続監視コスト**が乗る。個人 1 人・オンコールなし運用（brief (m)）にとって、「一度実装して終わり」ではなく「今後も国際的な法制度の帰趨を追い続ける」という **終わりのない義務を負う**ことになる点を、ops-risk レンズとして最も重く見る。①で述べた「見て意思決定に使う」運用すら怪しい機能に、これだけの初期・継続コストを払う費用対効果は極めて低いと判断する。

### ④ 段階論の確定: 「告知後」を正とし、「一定 DAU 到達後」は棄却する

4 択（現時点 / 告知前 / 告知後 / 一定 DAU 到達後）を他レンズの反論を踏まえて確定する。

- **現時点は棄却**: measurement-design の「自トラフィック除外のパラドックス」（`whiteboard.md:171`）と「母数 679 requests/週」（`whiteboard.md:172`）により、今入れても①で述べた通り死蔵する。
- **告知前は棄却**: 告知前は brief (n) の通り利用者が事実上オーナー本人のみで、②③で見積もったコスト（GA4 だけで最低 3SP、法務込みで 10SP 超）を払っても計測対象がほぼ存在しない。ROI が定義できない。
- **一定 DAU 到達後は棄却**: 段階公開の合意（`content/discussions/public-release-strategy-20260728/whiteboard.md:62` product-adoption Round 1）は「技術的公開」と「能動的告知」の分離のみを定義しており、**DAU 閾値という新しい未定義の判断基準を追加で発明することになる**。これは既存の合意（#171/#172/#179 クローズを前提条件とする段階公開）と重複する仕組みを新設する YAGNI 違反であり、判断基準を増やすこと自体が個人 1 人運用の認知負荷を上げる。棄却する。
- **「告知後」を正とする**: 理由は 3 点の収束による。(a) 告知によって初めて measurement-design が要求する統計的に意味のある母数が生まれる可能性が出る、(b) 段階公開の合意上、告知の前提条件として #171（本議論の②で GA4 より優先すべきと結論した MUST 未達）は既にクローズされている必要がある（`content/discussions/public-release-strategy-20260728/whiteboard.md:120,224` で security-legal・ops-cost の双方が独立に同じ結論）ため、**「告知後」を待てば #171 優先順位の問題は自動的に解消済みになる**、(c) privacy-legal が要求する越境移転開示（#190 との合流・`whiteboard.md:314`）も「告知して不特定多数に見られる」タイミングまでに整備すればよく、今すぐ整備する緊急性がない。

**結論**: 導入するなら「能動的告知後」。ただし③で見積もった法務・実装コスト（10SP 超・継続監視込み）を告知直前の準備タスクとして事前に見積もっておき、告知の意思決定と同時に GA4 導入の Go/No-Go も再評価する、という運びを推奨する。
