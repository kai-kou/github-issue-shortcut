## frontend-perf 反論（Round 2）

### 結論を先に更新
Round 1 では「gtag.js は不採用、採るなら Measurement Protocol（MP）」とした。Round 1 の 4 者を読んだ上で、**推奨をさらに 1 段階絞る: MP（Google 送信）より Workers Analytics Engine（WAE）を第一候補にする**。理由は measurement-design の低母数耐性論と、ops-risk④の ID 漏えいリスクが、WAE では構造的にほぼ消えるため（詳細は④で数字を出す）。ただし GA4 ダッシュボード UI がどうしても要るなら MP、という条件分岐は残す。

---

### ① measurement-design のイベント設計を実装すると性能予算にいくら乗るか（数字で）

measurement-design の Round 1 §2 の表（`login_complete` / `issue_form_ready` / `issue_submit_attempt` / `issue_submit_success` / `issue_submit_error` / `setup_complete`、`duration_ms` 付き）を、**gtag.js ではなく私が Round 1 §8 で提示した MP/WAE（Worker からの送出）で実装した場合** のコストを見積もる。

- **`duration_ms` の計算自体はクライアント側で必須**（`issue_form_ready` の `performance.now()` を state に保持し、送信完了時に差分を取るだけ）。これは既に `e2e/kpi.spec.ts` が `t0`/`tReady`/`t1` で行っているのと同型のロジック（measurement-design 自身が §2 末尾で指摘）。**新規ライブラリ import はゼロ**（`performance.now()` は Web 標準 API）。バンドル増分: **実質 0KB**（既存コードに数行の state 追加のみ、gzip/brotli 圧縮後は誤差レベル）。
- `issue_submit_attempt` / `issue_submit_success` / `issue_submit_error` は **既存の `/api/issues` POST に乗せる**（`duration_ms` `error_code` `launch_type` `has_labels` を既存リクエストボディに追加フィールドとして同梱するだけ）。**追加のネットワークリクエストもライブラリも不要**。ペイロード増分は JSON で数十〜150 バイト程度で、80KB brotli の JS バンドル予算とは無関係（これはリクエストボディであってバンドルサイズではない）。
- `issue_form_ready`（フォーム表示 = 起点イベント）は起票前に単独で送る必要があるため、**唯一の追加ネットワークリクエスト** になる。`navigator.sendBeacon()`（Web 標準・ライブラリ不要）で自前の軽量エンドポイント（例: `POST /api/telemetry`、数十バイト）に送り、Worker が MP/WAE へ中継する設計なら、**クライアント側バンドル増分はここでもほぼ 0KB**。
- `setup_complete`（login_complete と初回 issue_submit_success の突合）は measurement-design 自身が提案する通り「localStorage の 1 フラグ」で足りる。これは `offlineQueue.ts` が既に使っているのと同じ localStorage パターンで、**新規依存ゼロ**。

**結論（数字）**: measurement-design が要求する 6 イベント全部を実装しても、**client bundle への影響は実質 0KB（80KB brotli 予算の消費ゼロに近い）**。Round 1 で試算した「gtag.js フル対応 3〜5SP」との違いを明確にしておく — **重かったのは gtag.js というライブラリそのもの（135KB gzip）であって、イベント設計の複雑さではない**。イベント設計をどれだけ精緻にしても、MP/WAE 経由なら性能予算を圧迫しない。measurement-design のイベント設計は「削減すべき過大な要求」ではなく、**実装コストの観点では素直に採用してよい**（削減案は不要、という譲歩）。

一点だけ精度で押し返す: measurement-design #6（初回セットアップ完了率のクロスセッション計測）は、**localStorage 1 フラグでは同一ブラウザ内でしか判定できず、「別デバイスで再ログイン」等の真のクロスセッションは追えない**（`_ga` のような永続 Cookie が無いため）。これは性能コストの問題ではなく識別子設計の限界なので、privacy-legal の Cookie 最小主義（NFR-5〜7）と両立させるなら「単一ブラウザ内の近似値」で妥協するのが現実的、という評価をここに書いておく（②のコンセッションと合わせて後述）。

### ② privacy-legal の同意管理・データ最小化コストの見積もり

privacy-legal の 5 点セット（クエリ文字列遮断・ポリシー改訂・越境移転開示・EU 向け同意ゲート・DPA）のうち、**実装（コード）が必要なのはクエリ文字列遮断と同意ゲートの 2 点**。数字で見積もる。

1. **クエリ文字列遮断**（privacy-legal §4-1「`page_location` からクエリ文字列を除去」）: Round 1 §4 で私はどのみち SPA では `page_view` を手動送出する実装が必須と指摘済み（GA4 は自動発火しない）。**手動送出コードを書く時点で `location.pathname` を使うか `location.href` を使うかは 1 行の選択でしかない**。つまり privacy-legal の要求は frontend-perf が元々必要としていた実装の **追加コストゼロ**（同じ関数の中の別の引数を選ぶだけ）。良い意味で両者の要求が完全に重なる。
2. **同意ゲート（バナー UI + 送信前チェック）**: Consent Mode v2 は privacy-legal 自身が §5「広告機能を使わないなら Google 側の必須要件ではない」と整理済み。つまり **Google 公式の Consent Mode SDK/追加ライブラリは不要**、必要なのは①同意状態を保持する localStorage フラグ（`offlineQueue.ts` と同じパターン、新規依存ゼロ）②同意前は MP/WAE への送出 fetch を呼ばないガード（if 文 1 つ）③同意バナー UI コンポーネント（プレーンな div + 2 ボタン、既存の `translations.ts` に ja/en 文字列を追加するだけで新規 UI ライブラリは不要）。バナーコンポーネント自体のバンドル増分は数百バイト〜1KB gzip 程度（React コンポーネント 1 つ分）で、**80KB 予算には無視できるレベル**。見積もり: バナー UI 1SP + ゲーティングロジック 0.5SP + `translations.ts` への ja/en 追記 0.5SP ＝ **合計 2SP**。
3. **EU 限定表示にするかどうか**: privacy-legal は「EU からのアクセスを排除する仕組みが無い」と指摘しているが、実装上は **`request.cf.country`（Cloudflare Workers が無料で提供する地理情報、外部 GeoIP API 不要）を Worker が見て、EU/EEA/UK/スイス圏なら同意バナー表示フラグを立てて返す**、という実装が可能。追加コストは Worker 側の分岐 1 つ（0.5SP）。ただし「全員に同意バナーを出す」のが最も安全でシンプル（実装 0.5SP 減・法務リスクも下がる）なので、**推奨は地域判定なしの全員一律オプトイン**（privacy-legal の判断を優先しつつ perf/impl 観点では全員一律の方が安い、という提案）。

**結論（数字）**: privacy-legal のコンプライアンス要求（DPA 締結・ポリシー文面改訂などコード外の作業を除く）を実装しても、**追加バンドルは 1〜2KB gzip 程度**（バナー UI のみ）。80KB brotli 予算に対して無視できる規模であり、**性能予算を脅かしていたのは常に gtag.js というライブラリそのものであって、法務要求ではない** という Round 1 の結論を補強する。privacy-legal への回答: 5 点セットのうち実装が伴う 2 点は合計 2SP、性能への影響は無視できる水準。

### ③ ops-risk の撤去コスト・セルフホスト ID 混入への実装側の回答

ops-risk④（フォークしたセルフホスト利用者に計測 ID がハードコードされたまま残る問題）に対する具体的な実装回答:

- **私が Round 1 で推奨した MP/WAE（Worker からのサーバー送出）設計を採ると、この問題は構造的に発生しない。** gtag.js 方式では測定 ID（`G-XXXXXXX`）がクライアントバンドルに埋め込まれる（ビルド成果物に必ず含まれる）ため、フォークしたユーザーが差し替えを忘れると自動的に本家の ID へ送信され続ける。**MP/WAE 方式では測定 ID・API Secret はクライアントに一切出力されず、`wrangler.jsonc` の `vars`（`GITHUB_CLIENT_ID` と同じ既存パターン・`wrangler.jsonc:6-9` 参照）としてサーバー側にのみ存在する。**
- **安全なデフォルトの実装**: 環境変数が未設定の場合は計測送出そのものを no-op にする（`if (!env.GA_MEASUREMENT_ID) return;` の 1 行）。これにより **フォークしたユーザーは何もしなければ自動的に計測 OFF**（デプロイ時に自分の ID を明示的に設定しない限り送信されない＝ opt-in がデフォルト）。ops-risk が要求する「差し替え忘れが気づきにくい設定ミスになる」問題そのものを、gtag.js のような「常時 ON・埋め込み型」の設計を避けることで根本的に回避できる。追加実装コストは条件分岐 1 行で、Round 1 の MP 見積もり（2SP）に対する増分は無視できる。
- **撤去コスト（① への回答）**: Round 1 §9 の表の通り、MP/WAE 方式は `worker/index.ts` の該当関数を削除するだけで完了する（0.5SP 未満）。ops-risk が③で指摘する「コードは可逆でもレピュテーションは非可逆」という点は **その通りで、これは perf/impl レンズの守備範囲外（同意する）**。私が言えるのはコード面の可逆性のみで、そこは MP/WAE が最も優れているという事実を再掲するに留める。
- **ops-risk②（GA4 は NFR-14 の代替にならない）に完全同意**。実装コストの観点からも補強できる: NFR-14 の是正（Cloudflare Notifications 設定）は **コード変更ゼロ・ダッシュポードの数分の設定作業のみ**（0SP）。GA4/MP/WAE のどの経路を選んでも最低 2SP かかる本件より遥かに安く、かつ MUST 要件である。**工数の絶対順序として #171 を先に片付けるべきという ops-risk の結論に、実装コストの非対称性という別の角度から同意する。**

### ④ 実装方式の推奨を 1 つに絞る

Round 1 では「gtag.js は不可、採るなら MP」までだった。Round 2 で measurement-design の比較表（§3・低母数耐性・percentile・Cookie 不要）と ops-risk④（ID 漏えい）を踏まえ、**perf/impl レンズとしての最終推奨を Workers Analytics Engine（WAE）に一本化する**。理由（数字で）:

| 観点 | GA4 Measurement Protocol | Workers Analytics Engine |
|---|---|---|
| クライアント bundle 影響 | ゼロ | ゼロ（同じ） |
| Worker 外部 RTT | あり（`fetch()` で Google まで 1 往復、`waitUntil()` で非同期化必須・忘れると起票フロー遅延） | **なし**（`writeDataPoint()` は同一 Worker 内のバインディング呼び出しで、外部ネットワーク往復が発生しない） |
| 失敗の可視性 | **低**（本番エンドポイントは不正ペイロードでも常に 204。Validation Server を別途叩かないと壊れているか分からない） | 高（バインディングの型チェック・Wrangler のローカル検証が効く。書き込み失敗は Worker 側の例外として素直に拾える） |
| セルフホスト ID 漏えいリスク（ops-risk④） | 環境変数 + no-op デフォルトで緩和可能（③参照） | **同リスクなし**（Analytics Engine のデータセットは Cloudflare アカウント紐付けのバインディングで、フォーク先は自分の `wrangler.jsonc` を書かない限りそもそも動かない。measurement_id のような「うっかり残る秘密文字列」がコード上に存在しない） |
| 実装工数 | 2SP（①③参照） | 2SP 相当（バインディング追加 + クエリ層は自前構築が要るぶんで同程度、可視化ツールが無い分は ops-risk/measurement-design の運用判断） |

**perf/impl レンズからの結論**: 数字上は MP と WAE のクライアント負荷は同じ（ゼロ）だが、**Worker 内部の実装品質（RTT なし・失敗検知・ID 漏えい構造的排除）で WAE が明確に優る**。GA4 のダッシュボード UI という利点（ops-risk③・measurement-design§3 の「使い慣れた UI」）は運用レンズの判断に委ねるが、**実装・性能の観点だけで 1 つ選ぶなら WAE**。これは measurement-design の Round 1 結論と収束し、privacy-legal が要求する越境移転・同意ゲートの範囲（Google という第三者への送信自体を回避できるため、越境移転の論点そのものが消える可能性がある）を狭める効果もある（最終的な法的評価は privacy-legal レンズの判断）。

**総合推奨（frontend-perf レンズとして）**: adopt-conditional。ただし「GA4」ではなく「Workers Analytics Engine を第一候補、GA4 ダッシュボード UI が運用上どうしても必要な場合のみ MP」という条件分岐を、他レンズの結論（法務コスト・運用コスト）と突き合わせて統合案に反映してほしい。gtag.js 直挿しは全レンズ通してどこにも支持材料が無く、確実に不採用。
