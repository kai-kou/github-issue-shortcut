## 1. 公開したときに「保持することになる」情報の棚卸し

保持先は 3 層に分かれる。**自分で消せるのは A 層だけ** で、B 層（Cloudflare 基盤）と C 層（利用者端末）は設計で減らすしかない。

### 1-A. 自前 D1 に保存されるデータ（`migrations/` の 8 テーブル）

| テーブル | 保持する情報 | 個人データ性 | 実装上の削除タイミング |
|---------|------------|------------|------------------|
| `users` | GitHub ユーザー ID・login 名・アバター URL・作成日時 | **識別子そのもの**（GitHub 上の公開情報と同値） | アカウント削除時のみ |
| `sessions` | セッション ID の SHA-256 ハッシュ・作成 / 失効 / 最終利用時刻 | 生 ID は Cookie 側のみ。`last_used_at` は **行動時刻の記録** | ログアウト・アカウント削除時のみ（**期限切れ行の自動削除なし**） |
| `tokens` | GitHub アクセストークン・リフレッシュトークン（AES-256-GCM 暗号化）・各有効期限 | **最高機微**（復号できれば本人として GitHub 操作が可能） | アカウント削除時のみ（**ログアウトでは残る**） |
| `shortcuts` | ユーザーが登録したリポジトリ名（`owner/repo`）・ラベル・定型タイトル・表示名 | **private リポジトリ名や案件名が平文で残る** | 個別削除・アカウント削除時 |
| `issue_log` | `SHA-256(repo + title + body + labels)` のハッシュ・リポジトリ名・作成時刻 | 本文平文は保存しない（NFR-17 準拠）。ただし **リポジトリ名と起票時刻は平文** | Cron で 7 日経過後に削除（唯一の自動削除） |
| `request_ids` | クライアント生成の再送防止 ID・作成時刻 | 起票 1 件 = 1 行の **行動ログ相当** | **自動削除なし（無期限に蓄積）** |
| `rate_limits` / `shortcut_rate_limits` | ユーザー ID・60 秒ウィンドウ開始時刻・回数 | **分単位の利用時刻履歴** | **自動削除なし（無期限に蓄積）** |

**ポイント**: プライバシーポリシーは「アカウントが存在する間、上記データを保持します」と書いており嘘ではないが、実装は
「**アカウントが存在する限り、利用のたびに行動記録が増え続け、機能的にはもう不要になっても消えない**」状態にある（§3-R3）。

### 1-B. Cloudflare 基盤側に自動的に残るデータ（自分の DB の外）

| データ | 内容 | 保持期間 | 現状の設定 |
|-------|------|---------|-----------|
| Workers Logs（invocation logs） | Worker 実行リクエストのメタデータ（リクエスト / レスポンス情報と Cloudflare 側のコンテキスト） | 無料 3 日 / 有料 7 日 | `wrangler.jsonc` に `observability` 記述なし。公式は「**新規 Worker は既定で有効**（`enabled` は新規 Worker で既定 true）」と明記 → **既定 ON と考えるのが安全**。サンプリングは既定 100% |
| D1 Time Travel | データベースのポイントインタイム復元履歴 | 無料 7 日 / 有料 30 日・**常時 ON・無効化不可** | 既定のまま |
| Cloudflare のリクエストログ / アナリティクス | IP アドレスを含むエッジ側の処理記録（Cloudflare が処理者として保持） | Cloudflare のポリシー準拠 | 制御不可 |

**含意 1**: アプリ側で `console.log` を 1 行も書いていなくても、**リクエスト単位のメタデータは Cloudflare 側に数日残る**。
「ログは一切取っていません」とは言えない（プライバシーポリシーにこの層の記載がない = §4 の齟齬）。

**含意 2**: `share_target` は `GET /new?title=...&body=...&url=...`（`vite.config.ts`）なので、**共有した記事タイトル・URL がクエリ文字列に載る**。
`/new` は `run_worker_first` の対象外で静的アセット配信に落ちるため、通常は Worker の invocation log は生成されない想定だが、
**エッジ側のリクエスト記録には URL として渡る**。ここは公開前に実機で「Workers Logs に `/new?...` が出るか」を確認しておきたい（要検証項目）。

**含意 3**: Time Travel が常時 ON である以上、「アカウント削除で即時に消えます」という説明は
**アプリから見た即時削除は真だが、基盤の復元履歴からは無料 7 日 / 有料 30 日は消えない**。ポリシー文面はこの粒度に合わせるのが正確。

### 1-C. 利用者の端末に残るデータ

`localStorage` にログイン情報キャッシュ・リポジトリ一覧・ラベル・ショートカット・最近使ったリポジトリ・下書き、
Service Worker のキャッシュにアプリシェルとオフラインキューが残る。**private リポジトリ名が端末に平文で残る** 点は共有端末で意味を持つ。
ログアウト時にクリアされるのは `authCache` / `reposCache` / `shortcutsCache` の 3 つで、
`recentRepos`・ラベルキャッシュ・下書き・オフラインキューは残る（`src/auth/useAuthState.ts`）。

## 2. 「持つこと」で発生する責任の所在

現状構成では、**運営者（あなた）が GitHub のトークンを預かる中継者** になる。ここが公開の本質的なリスク源で、次の 3 点に要約できる。

1. **預かるのは「鍵」であって「データ」ではない**: D1 に貯まる業務データ自体は薄い（ハッシュと設定値）。重いのはトークンで、
   これが漏れると **その利用者が App をインストールした private リポジトリの Issue を読み書きできる**（GitHub App の `Issues: write` は読み取りを含む）。
2. **1 つの App で全ユーザーが動いている**: 誰か 1 人のスパム起票で GitHub App 自体が制裁・停止されると、**全ユーザーが同時に使えなくなる**。
3. **無料枠は「上限に当たると止まる」設計**: 課金で吸収されない代わりに、超過したその日は全ユーザーが起票できない（§5-3）。

## 3. リスク評価（現状構成のまま公開した場合）

深刻度は「発生確率 × 影響」で、公開直後の個人〜小規模利用を前提に付けた。

| # | リスク | 深刻度 | 現状の緩和策（実装済み） | 残っている穴 |
|---|-------|-------|--------------------|------------|
| **R1** | **トークン失効・鍵ローテーション不能**: `worker/crypto.ts` は鍵 ID を持たず暗号文が単一鍵に固定。鍵を替えると既存トークンが全件復号不能 | **高** | AES-256-GCM でアプリ層暗号化・鍵は Workers Secrets（D1 とは別管理） | 鍵漏洩・定期ローテーションの際に **全ユーザー強制再ログイン以外の手段がない**。二重鍵（`v1:` プレフィックス等）での移行導線が未実装 |
| **R2** | **Cloudflare アカウント侵害 = 全ユーザーのトークン露出**: D1 と暗号鍵が同一アカウント配下にあり、アカウントを取られると分離が意味を失う | **高** | Secrets とデータの物理分離・トークン以外は平文保存しない | アカウント保護（ハードウェアキー MFA・API トークンの最小権限化・Workers Builds の権限確認）が **運用手順として明文化されていない**。侵害検知の手段もない |
| **R3** | **消えない個人データの蓄積**: `request_ids` / `rate_limits` / `shortcut_rate_limits` / 期限切れ `sessions` に削除処理がない（Cron は `issue_log` のみ） | 中〜高 | `issue_log` は 7 日で削除・本文平文は非保存 | 目的を終えたデータが残り続ける。**データ最小化の原則（APPI の消去努力義務・GDPR 5(1)(e)）とポリシー文面の両方に対して弱い**。コストも逓増（§5-5） |
| **R4** | **ログアウトしてもトークンが残る**: `deleteSession` はセッション行のみ削除し `tokens` 行は残置 | 中 | アカウント削除では全テーブル削除される | 「もう使わない」利用者のリフレッシュトークン（最長 6 か月）が残る。**休眠ユーザーの自動失効ジョブがない** |
| **R5** | **スパム起票による GitHub App 停止**: 1 ユーザーの悪用が全ユーザーに波及 | 中 | ユーザー単位 10 件/分（`/api/issues`）・20 件/分（ショートカット）・重複起票防止・全操作 GitHub 認証必須 | **日次・月次の上限がない**（理論上 1 ユーザー 14,400 件/日）。要件 PR-5（422 = spam 判定の連発を検知して自動抑止）は **未実装** |
| **R6** | **`workers.dev` 運用ゆえのエッジ防御の欠如**: ゾーン機能（WAF・Rate Limiting Rules・Bot 管理・Turnstile のエッジ適用）が使えない | 中 | アプリ層レート制限・API は全て認証必須（未認証は 401 で早期終了） | 未認証フラッドでも **リクエスト数は消費する**。無料枠なら日次上限到達で全停止、有料なら請求が伸びる。**予算アラート・使用量監視が未実装**（NFR-14 の「枠超過が近づいたら検知できること」が未達） |
| **R7** | **ポリシー文面と実装の齟齬**（過少・過剰の両方） | 中 | 利用規約・プライバシーポリシーを日英で公開済み・アカウント削除実装済み | ①「最小限の計測イベントを収集」と書いてあるが **計測は未実装**（過剰申告）、② Workers Logs / Time Travel など **基盤側保持の記載なし**（過少申告）、③ 越境移転・問い合わせ窓口・事業者表記の記載なし（§4） |
| **R8** | **端末に残る private リポジトリ名**: `localStorage` / SW キャッシュ | 低〜中 | ログアウトで主要 3 キャッシュはクリア | `recentRepos`・ラベルキャッシュ・下書き・オフラインキューはログアウト後も残る |
| **R9** | **データ所在地の非制御**: D1 に jurisdiction 未設定 | 低 | — | 保存地域を EU / FedRAMP 等に固定できない（現状は指定なし）。日本ユーザー向け説明では「海外保存」と明示するのが正確 |
| **R10** | **障害時の一人運用**: 監視・通知・オンコールなし | 低〜中 | 利用規約に無保証・サービス変更/終了の可能性を明記済み | 障害に気づく手段がない（可用性監視・エラー率アラートが未設定） |

### リスクの優先順位（公開前に埋めるべき順）

1. **R6 + R2（守りの土台）** — 予算アラートと Cloudflare アカウント保護は、実装コストが最も小さく、失敗時の損失が最も大きい。
2. **R3 + R4（保持しないという最良の防御）** — Cron に削除処理を足すだけで、漏洩時の被害範囲も法務上の説明も同時に軽くなる。
3. **R7（言っていることと実装を合わせる）** — 公開の前提条件。文面修正のみで済む。
4. **R5 / R1（運用の持続性）** — 利用者が増えてから効いてくる。公開直後は必須ではない。

## 4. 法務・コンプライアンス面の論点（一般的整理・専門家確認推奨）

| 論点 | 現状 | 公開時に必要になりうる対応 |
|------|------|------------------|
| 日本の個人情報保護法（APPI）: 利用目的の特定・公表 | プライバシーポリシーに記載あり | 概ね充足。ただし「計測イベント」の記述は実装と一致させる |
| APPI: 外国にある第三者への提供（28 条） | Cloudflare（米国企業）に保存する旨のみ記載 | 委託であっても外国事業者への提供として整理されるのが一般的。**本人同意 or 相当措置に関する情報提供**（移転先国・当該国の制度・講じている措置）の追記が要検討 |
| APPI: 保有個人データに関する公表事項（32 条） | 事業者名・連絡先・開示等請求の手続きの記載なし | **連絡先（問い合わせ窓口）の明記** が実務上の最小線。個人開発でも窓口は要る |
| APPI: 安全管理措置 | 暗号化・最小権限・セッションハッシュ化は実装済み | 措置内容を **ポリシーに 1 段落で記述**（暗号化・アクセス制限・削除手段） |
| GDPR（EU 圏の利用者が使った場合） | 対応の明示なし | 管理者としての連絡先・法的根拠（契約の履行）・保持期間・データ主体の権利（削除は実装済み / **開示・可搬性は未実装**）。Cloudflare 側は標準 DPA でカバーされる前提 |
| Cookie 同意 | セッション Cookie のみ（`__Host-` + HttpOnly + SameSite=Lax）・トラッキング Cookie なし | 厳密に必要な Cookie のみのため **同意バナーは原則不要**。この状態を維持する（＝安易にアナリティクスを入れない）ことが最良の選択 |
| GitHub 側の要件（PR-6） | GitHub App の public 設定・説明・権限理由・PP URL の整備 | 公開前チェック。**要求権限を `Issues: write` に保つこと自体が最大の信頼材料**（利用者から見た導入判断の決め手） |
| 特定商取引法 | 無償提供のため原則対象外 | 課金を導入する場合は再検討 |

> **法務まわりで一番コスパが良いのは「保持しない」こと**（R3 / R4 の解消）。持たないデータには説明義務も漏洩リスクも発生しない。

### 5-2. 1 アクティブユーザーあたりの消費量（実装から算出）

| トークン自動リフレッシュ（8 時間ごと） | 1 行 | 3 行（ロック取得・保存・解放） | — |

| Cron の `issue_log` 削除（起票 1 件につき 7 日後） | — | 2 行（行 + インデックス） | — |

### 5-4. ユーザー数が増えたときの推移

**（a）無料プランのままの天井** — 最初に当たるのは **D1 の書き込み 10 万行/日**。

| 制約 | 上限 | 換算 DAU（ヘビー利用前提） |
|------|------|------------------------|
| **D1 書き込み 10 万行/日** | — | **約 2,400 DAU** ← 最初の天井 |
| Workers リクエスト 10 万/日 | — | 約 6,600 DAU |
| Workers Logs 20 万/日 | — | 約 13,000 DAU |
| D1 読み取り 500 万行/日 | — | 約 11 万 DAU |

→ **無料プランの実効上限は安全率込みで約 2,000 DAU**（DAU/MAU 比 20〜30% なら **MAU 7,000〜1 万人**）。
起票頻度が低い一般ユーザー中心なら、この数倍は伸びる。

**（b）有料プラン（$5/月）で追加課金が発生し始める点** — 込み枠 1,000 万リクエスト / 5,000 万書き込み。

| 制約 | 込み枠を使い切る DAU |
|------|------------------|
| Workers リクエスト 1,000 万/月 | 約 22,000 DAU ← 最初 |
| CPU 3,000 万 CPU-ms/月 | 約 33,000 DAU |
| D1 書き込み 5,000 万行/月 | 約 40,000 DAU |
| Workers Logs 2,000 万/月 | 約 44,000 DAU |

→ **$5/月のまま約 2 万 DAU まで運用できる**。

**（c）スケール表（現状実装のまま・最適化なし）**

| DAU | 月間リクエスト | 月間 D1 書込 | 概算月額（$1 = 150 円） |
|-----|-------------|------------|--------------------|
| 100 | 4.5 万 | 12.6 万 | **$0（無料枠内）** |
| 1,000 | 45 万 | 126 万 | **$0（無料枠内・ただし日次書込は上限の 42%）** |
| 2,400 | 108 万 | 302 万 | **無料枠の限界 → $5 の有料化が必要** |
| 10,000 | 450 万 | 1,260 万 | **$5（約 750 円）** |
| 22,000 | 990 万 | 2,772 万 | **$5（込み枠ぎりぎり・約 750 円）** |
| 50,000 | 2,250 万 | 6,300 万 | 約 **$24（約 3,600 円）** |
| 100,000 | 4,500 万 | 1.26 億 | 約 **$113（約 1.7 万円）**（+ストレージ逓増） |
| 1,000,000 | 4.5 億 | 12.6 億 | 約 **$1,600〜1,800（約 25 万円）** |

内訳の傾向: **10 万 DAU 規模になると D1 書き込みが総額の約 7 割**、次いで Workers Logs が約 1 割強。
リクエスト数と CPU は最後まで安い（Cloudflare は帯域・エグレス課金がないため配信量は無料）。

### 5-5. 見落としやすいコスト: 消えないデータのストレージ

`request_ids` と `rate_limits` に削除処理がないため、**利用者が増えなくても、使い続ける限りストレージが単調増加する**。

| DAU | 1 年後の蓄積 | ストレージ月額（5 GB 超過分） |
|-----|-----------|------------------------|
| 1,000 | 約 0.15 GB | $0（無料枠内） |
| 10,000 | 約 1.5 GB | $0（無料枠内） |
| 100,000 | 約 15 GB | 約 **$7.5/月**（2 年目 約 $19/月・以後も逓増） |

金額は小さいが、**「消し方が実装されていないデータが増え続ける」構造そのもの** が R3 のリスク本体である（コストは症状にすぎない）。

### 5-6. コスト最適化の余地（実施すれば約 1/3 に圧縮できる）

| 施策 | 効果 | 副作用 |
|------|------|-------|
| `sessions.last_used_at` の更新を「前回更新から 1 時間以上経過時のみ」に間引く | **D1 書き込みを約 60% 削減**（最大の効き目） | セッション最終利用時刻の精度が落ちる（用途は失効判定のみなので実害なし） |
| `observability.head_sampling_rate` を 0.05〜0.1 に設定 | Workers Logs を 90〜95% 削減（**プライバシー面でも有効**） | 障害調査時のログ密度が下がる |
| `request_ids` / `rate_limits` / 期限切れ `sessions` の Cron 削除を追加 | ストレージ逓増を停止・R3 も同時に解消 | 削除ぶんの書き込みが発生（読み取り・保持より安い） |
| Workers のレート制限バインディングでアプリ層カウンタを置換（要検証） | 起票あたりの D1 書き込みを 1 行削減 | 分散カウンタの精度・仕様の事前検証が必要 |

## 6. 結論: 「今のまま公開する」と何が起きるか

### 成立する範囲

- **技術・コスト面は問題にならない**。無料枠のまま **約 2,000 DAU**、$5/月で **約 2 万 DAU** まで到達できる。
  1 ユーザーあたり月 0.25 円、1 起票 0.0015 円で、**バズっても破産しない構造**（そもそもコストが天井ではない）。
- 認証・暗号・重複防止・レート制限・法務ページ・アカウント削除といった **公開の必須要件は一通り実装済み** で、
  「作りかけを公開する」状態ではない。

### 公開前に埋めておきたい最小セット（費用ゼロ・工数小の順）

1. **Cloudflare の予算アラート / 使用量監視の設定**（R6・NFR-14 未達分）— 上限に当たったことに気づけない状態を先に解消する。
2. **Cloudflare / GitHub アカウントの MFA 強化と API トークンの権限最小化**（R2）— 侵害されたら暗号化は意味を失う。
3. **プライバシーポリシーの実装整合**（R7）— 「計測イベント」の記述修正、基盤側ログ・復元履歴（Time Travel）の保持、越境保存、問い合わせ窓口の追記。
4. **保持期間の実装**（R3・R4）— Cron に `request_ids` / `rate_limits` / 期限切れ `sessions` の削除と、
   長期未使用ユーザーのトークン失効を追加する。持たないデータは漏れない。

### 増えてから対応でよいもの

- 起票の日次上限と 422 連発ユーザーの自動抑止（R5・PR-5）
- 暗号鍵のローテーション導線（R1・二重鍵移行）
- カスタムドメイン化による WAF / Rate Limiting Rules の適用（R6 の本格対応）
- `last_used_at` 間引きとログサンプリング（§5-6・数千 DAU を超えてからで十分）

### 残る要検証項目

- `share_target` 経由の `/new?title=...&body=...` が Workers Logs に記録されるか（静的アセット配信のため通常は記録されない想定・実機確認したい）
- Workers Logs（`observability`）の現在の有効状態と、有効なら `head_sampling_rate` の初期値
- GitHub App が public 設定になっているか、説明文・権限理由・PP URL が整備されているか（PR-6）
