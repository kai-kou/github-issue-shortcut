# サブエージェント・エージェントチーム活用ルール（サマリー版）

> 完全版は `docs/rules/agent-team.md`（Haiku 推奨スキル一覧・モデル指定方針の SSOT・プロジェクト固有オブザーバー詳細）。

## 2 協調モードと振り分け（最重要・常駐）

「エージェントチーム / 専門チーム」には実装が **2 つ** あり、混同しやすい。必ず区別する。

| モード | 実体 | 議論 | 既定で使う場面 |
|--------|------|------|--------------|
| **役割分担型 fan-out** | `Agent` ツールの並列サブエージェント（メインが集計） | なし | 内部の自動調査・速度/コスト優先。障害調査（`problem-investigation-protocol.md` Step 3）・定型チェック |
| **議論型（ネイティブ Agent Teams）** | `discussion-review` スキル: メインが lead、参加者は name 付き background `Agent` + `SendMessage` + 共有ホワイトボード | あり（相互に反論・検証） | **ユーザーが明示的に「専門チームを組成して」と指示したとき**・過剰指摘削減が要るレビュー |

**振り分けルール（SSOT・飼い主決定）**

- ユーザーが「専門チームを組成して」「チームで議論して」等と明示したら **議論型（`discussion-review` スキル）が既定**。fan-out で代替してよいのは、コスト/速度優先の明示があるか、議論に値しない軽微なタスクのときだけ（理由を 1 行述べる）
- 議論型の実行前に `discussion-whiteboard-rules.md` を Read し、`discussion-review` スキルの手順に従う
- **障害検出時の内部自動調査は fan-out が既定**（ユーザー明示指示ではないため）
- フォールバック連鎖: ネイティブ失敗 → `tools/run_discussion_review.py`（claude -p 駆動）→ それも失敗なら fan-out。各段の退避をログに残す（サイレントフォールバック禁止）

## モデル選択（コスト最適化）

> 🔴 **モデルは「エイリアス」で指定し、厳密バージョン ID を運用ファイルに書かない**（世代交代時の修正が不要になる）。
> 例外は ① API 直叩き ② 料金表など ID をキーにする実装 ③ 意図的なピン留め。SSOT: `agent-team.md`「モデル指定の方針」。

| 用途 | モデル | effort |
|------|--------|--------|
| 知能重視タスク（長文生成・複雑な設計判断） | `opus` | `/effort xhigh`（明示指定。既定は `high`） |
| メインセッション・実装・PR 対応 | `sonnet` | `/effort medium` |
| 調査・検証・チェック（サブエージェント） | `haiku` | — |
| 一区切りに収まらない最難関・超長時間タスク | `fable`（高コスト・既定にしない） | `/effort high`〜 |

**原則**: 迷ったら `sonnet`。`opus` は明確に必要な場合のみ（`.claude/settings.json` の既定が `sonnet` なのは意図的）。コスト削減はまず effort を下げて評価する。詳細は `claude-code-optimization.md`。

## サブエージェント使い分けと並列化

| 状況 | subagent_type | model |
|------|--------------|-------|
| コードベース探索・ファイル検索 | `Explore` | `haiku` |
| 実装計画・設計 | `Plan` | `sonnet` |
| 実装・API 呼び出し | `general-purpose` | `sonnet` |
| 検証・パターン検索 | `general-purpose` | `haiku` |

- 独立した作業は **並列** で同時実行する（依存があるときだけ逐次）
- サブエージェントは成果物全文でなく **1,000〜2,000 トークンのサマリー** を返す
- **重要な出力は候補を並列生成してから選ぶ**（Verbalized Sampling）: タイトル・冒頭フック・設計案など「最初の 1 案がそのまま採用される出力」は、Haiku 3〜5 本で角度の異なる案を同時生成し、選択基準を当てて選ぶ。選択理由を 1 行記録する（1 案直行は Anchoring を招く）
- `isolation: "worktree"`: 並行して同じファイルを触る変更を隔離する（変更なしなら自動クリーンアップ）
- `run_in_background: true`: 完了時に通知が来る（`sleep` ポーリング禁止）。**push 系を委譲したら必ず `mcp__github__get_file_contents` 等で結果を検証する**（L-080）

## Haiku サブエージェント向けプロンプト先頭テンプレート

> Haiku は Claude 5 世代ではないため、**明示的な出力ルールを省略しない**（「判断に委ねる」方針の適用外・#326）。

```
# 出力ルール（必ず守ること）
- 箇条書き・要点のみ（詳細説明・前置き・謝辞は省略）
- ファイル全文でなくパスと行番号のみ返す
- 結果は1,000〜2,000トークン以内
```

## 成果物の受け渡し（揮発チャネル禁止・L-121）

親が受け取れるのは **サブエージェントの「最後の」assistant テキストだけ**。報告後に継続プロンプトが
注入されると相槌（`完了。` / `End.`）が最終テキストを上書きし、所見が丸ごと失われる（実測・#140）。

- 失うとやり直しになる成果物（レビュー所見・調査結果）は **ファイルに書かせ**、最終メッセージは
  `WROTE: {絶対パス} ({N}件)` の 1 行にする（議論型はホワイトボードが同じ役割）
- 空・一言の戻り値を「指摘なし」「異常なし」と解釈しない（未実施を成果ゼロと報告する捏造・L-113）。
  回収漏れは生トランスクリプト（`tasks/<agentId>.output`）の assistant text を全件確認して回収する
- サブエージェントに `ReportFindings` を使わせない（親セッションに届かない）

## プロジェクト固有レビュー・監修エージェント

`.claude/agents/` に定義する（例: 技術正確性レビュー役・初心者目線チェック役）。参加レベルは Lv1（一言）/ Lv2（箇条書き 3-5 点）/ Lv3（構造化レポート）。critical 指摘は自動ゲート扱い（修正必須）。
